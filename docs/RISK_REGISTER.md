# RISK_REGISTER.md — Metrivio X Growth Engine

Each risk is rated Likelihood (L/M/H) × Impact (L/M/H), with a mitigation and an owner-decision note where the founder needs to make an explicit call rather than have one made silently in code.

---

## 1. Platform Policy Risk — Automated Outreach & Engagement

**Risk:** X's Terms of Service and Automation Rules restrict bulk automated engagement (mass follow/unfollow, automated liking at scale, unsolicited automated DM campaigns) and platform manipulation more broadly. A cold-outreach system that DMs discovered prospects — even a well-targeted one — sits inside the category of automated messaging X's rules are written to constrain, and this risk scales with volume and pattern.

**Decision on record:** the founder has explicitly decided that automated X prospecting and automated X outreach, including DM sending, are wanted capabilities of this system and should not be removed or architecturally restrained because of this risk. This document is no longer proposing that the system avoid or minimize outreach automation — it is documenting the risk honestly so the operating controls below are used deliberately, not as a reason to withhold the feature.

**Likelihood:** Medium-High if volume/pattern is aggressive and undifferentiated; Low-Medium if targeted, evidence-based, and paced conservatively — the architecture is built to make the latter the easy default without blocking the former if the founder chooses it.
**Impact:** High — account suspension would take down both the outreach channel and the content/publishing channel if they share an account. This impact rating is exactly why the controls below exist as real, working mechanisms rather than cosmetic settings.

**Controls built into the architecture (all configurable, all real, none of them a substitute for the founder's own risk-tolerance judgment):**
- `automation_mode` (`dry_run` / `approval_required` / `autonomous`), independently settable for outreach, with `autonomous` fully implemented and tested as a supported end state (ARCHITECTURE.md §7).
- Per-action-type daily/action limits (DMs, follows, scrapes), persisted across restarts, editable in Settings.
- A Session Health Monitor (ARCHITECTURE.md §3.5) that watches error rate, auth failures, and rate-limit headroom on the connected account and can automatically pace down or drop to `approval_required` if the account shows signs of strain — itself a configurable behavior (`session_health_auto_downgrade`), so even this safety net is the founder's choice, not a hardcoded ceiling.
- A global kill switch that overrides every other setting instantly.
- Evidence-gated personalization, which naturally differentiates this system's outreach from spam/bulk-blast patterns, since a message cannot be generated without a real, sourced reason for contacting that specific person.
- Full audit logging of every send, every mode change, and every health-state transition, so account behavior is reviewable after the fact regardless of which mode was active.
- Bulk mass-follow/unfollow, auto-like farming, and auto-commenting (as distinct from targeted, evidence-based DM/reply outreach) remain out of scope — not because outreach automation is restrained, but because those specific mechanics are a different capability (visibility/growth gaming) than what this system is built to do, and they are the parts of X's rules most clearly and unambiguously written against, with the least defensible "this is targeted communication, not spam" argument available.

**Owner decision needed:** volume/pacing (how many DMs/day, from which account, how aggressively to ramp) is a business risk-tolerance call the founder makes through Settings, not something the code decides. The system supports any point on that spectrum, including fully autonomous, high-volume operation if that's the founder's choice — the recommendation to start conservative and watch the Session Health signal before increasing is a suggestion, not an enforced constraint.

## 2. Platform Policy Risk — Scraping (Read Side)

**Risk:** Reading public profile/tweet/search data via unofficial GraphQL access (XActions) is lower-risk than automated writes but still not X's officially sanctioned access path, and X periodically changes endpoints specifically to break unofficial scraping.

**Likelihood:** Medium (endpoint changes are described industry-wide as happening every 2–4 weeks).
**Impact:** Medium — breaks discovery/enrichment until the adapter is updated or swapped; does not directly risk account suspension for read-only, unauthenticated public data access, but does risk suspension if scraping is done from a *logged-in* session at high volume/velocity.

**Mitigations:**
- `XReadAdapter` isolation means an endpoint break is a contained, fixable failure, not a system-wide outage.
- Rate limits and human-like pacing on any logged-in scraping (followers/following require login per XActions' own docs).
- Fallback adapter (twscrape) documented as a second implementation path if XActions read reliability degrades.
- Discovery/enrichment jobs log zero-result runs distinctly from "job didn't run," so an endpoint break is visible quickly rather than silently returning empty data that looks like "no prospects found."

## 2A. Stage 4A Implementation Findings — Kill-Switch Scope, Vendoring, and a Verified-Not-Live-Tested Behavior

**Kill-switch scope extended to X reads (policy decision, not a redesign).** ARCHITECTURE.md §7 documents the kill switch as covering "every write-adapter call." Stage 4A implements the founder-approved policy that it should also cover `XReadAdapter` reads, since bulk reads carry real account-restriction risk per XActions' own disclaimer (§2 above), not just writes. This was done as the smallest possible call-site change — `XActionsReadAdapter.getProfile`/`searchTweets` each call the existing, unmodified `KillSwitch.assertNotActive()` before any network call — not a change to `KillSwitch`'s own implementation. Future write-adapter implementations already do (or will do) the same; this just extends the same check to the read side for this one adapter.

**Vendoring dependency-footprint finding (confirmed, not assumed).** Direct source inspection of `nirholas/xactions` at the pinned commit found that its read-only HTTP scraper module (`src/scrapers/twitter/http/*`) has **zero third-party npm dependencies** beyond Node built-ins — it does not touch any of the root package's 30 dependencies (Puppeteer, Prisma, Stripe, Redis, Express, JWT/bcrypt, etc.). Vendoring only that subtree (`packages/adapters/vendor/xactions-http/`, see its own `VENDOR.md`) means Stage 4A added **zero new npm packages** to this repository's dependency tree — verified via `npm install` reporting the same package count before and after, and via `package-lock.json` showing no diff.

**Contract gap, documented rather than silently resolved:** the existing `XReadAdapter` interface has no `getProfileById`-equivalent method, even though the underlying XActions library supports profile lookup by numeric user ID (`scrapeProfileById`) as well as by handle. Stage 4A does not add one — extending the interface was out of scope ("do not unnecessarily modify the core adapter interface"). If a later stage needs ID-based lookup (e.g. re-resolving a prospect whose handle changed, using the already-stored `x_user_id`), this is the exact, minimal interface addition that would be needed — flagged here rather than added speculatively.

**Additive design applied, documented per instruction:** `XReadAdapter`'s existing methods return bare result types with no status/error model, unlike Stage 2's `TechAnalyzerResult.scanStatus`. Rather than widening those return types (an interface change), Stage 4A added five generic, adapter-agnostic error classes (`XReadRateLimitedError`, `XReadAuthenticationRequiredError`, `XReadNotFoundError`, `XReadNetworkError`, `XReadUnexpectedError`) to `packages/core/src/adapters/x-read-adapter.ts`, thrown instead of ever collapsing a real failure into an empty successful result — mirroring the existing `KillSwitchActiveError`/`NotImplementedInStage1Error` pattern already used elsewhere in this codebase. This is additive only; `XReadAdapter`, `ProfileResult`, `TweetResult`, `AccountResult`, and `XReadOptions` are all unchanged.

**Verified from source, not from a live call — flagged explicitly, not claimed as confirmed working.** This sandbox's egress policy blocks arbitrary outbound HTTP (confirmed directly in earlier stages of this project), so no live X request was made or could be made. Reading `TwitterHttpClient`'s constructor and XActions' own `createHttpScraper()` convenience factory, a bare client with no cookie supplied appears to be upstream's own intended "guest mode" (no separate guest-token acquisition step is performed for the no-cookie case in that factory). This is stated as source-verified, not live-verified — the first real integration test against live X data should specifically confirm guest-mode reads actually succeed before this is relied upon in a discovery pipeline.

## 2B. Stage 4B Implementation Findings — Discovery Architecture, Config, and Known Limitations

**Discovery architecture.** `packages/prospecting/src/discovery/discovery-service.ts`'s `DiscoveryService` implements the read-only pipeline: configured search query (via the existing `XReadAdapter`, never XActions directly) → deduplicated candidate usernames → profile retrieval → deterministic founder/CEO classification (`founder-classifier.ts`, no LLM) → conservative company/domain extraction (`company-domain.ts`) → prospect upsert → discovery provenance (`prospect_sources`) → fixed-category evidence (`evidence`) and pain-signal observations (`pain_signals`) → `job_runs` checkpoint. No new database tables — every one of `prospects`, `prospect_sources`, `evidence`, `pain_signals`, `job_runs` already existed with exactly the columns/enums this stage needed (`prospects.source` already included `founder_search`/`pain_intent_search`; `pain_signals.topic` already defined the exact CAC/ROAS/MER/attribution/budget_allocation/channel_performance/profitability vocabulary reused here verbatim).

**Kill switch: no new wiring, by design.** `DiscoveryService` depends only on the `XReadAdapter` interface and never constructs or references `KillSwitch` itself — kill-switch protection is inherited transparently through whichever concrete adapter is injected (in production, the already kill-switch-protected `XActionsReadAdapter` from Stage 4A). Tested by injecting a scripted adapter that throws the real `KillSwitchActiveError` and confirming `DiscoveryService` records it as a distinct, visible error rather than silently treating the run as "zero candidates found."

**Request budget reuses the existing `daily_limit_scrapes` config key** (`SystemConfigService.getDailyLimit('scrapes')`) rather than a new budget mechanism — one increment per search call and per profile call. **Known simplification:** this is enforced per-run only; there is no cross-run daily aggregate counter (no table currently tracks "scrapes used so far today" across separate job runs), so a very literal reading of "daily" limit enforcement is not fully implemented. Flagged here rather than silently assumed complete — a future stage adding true cross-run daily tracking would need a small counter table or a date-keyed `system_config` value.

**Evidence scope deliberately narrow — most ICP factors are structurally unreachable from X discovery alone.** Per this stage's explicit conservatism instructions, `DiscoveryService` only ever writes three evidence shapes: (1) `decision_maker_signal` role-tier facts from bio classification, (2) `company_identification` from the profile's own website field, (3) `paid_acquisition_signal` → `paid_media_job_posting_90d`, and only via a narrow matcher requiring an explicit paid-media title (media buyer/growth marketer/paid social specialist/performance marketer/paid media manager), explicit hiring language, and a verified 90-day-old-or-newer tweet date — a generic "we're hiring" tweet never qualifies (tested). It **never** writes `revenue_signal`, `dtc_signal`, or `trigger_signal` evidence under any circumstance (tested explicitly, including adversarial bios/tweets naming a specific revenue figure, high follower counts, Meta/Google mentions, and "we are scaling" language) — matching RESEARCH.md §2A.11's own finding that no tool in this stack is a legitimate source for those categories from X data alone, and this stage's explicit instruction not to invent trigger evidence from a single-observation "current state" tweet.

**All discovery-sourced evidence is tagged `LIKELY`, never higher.** Per ICP §4's own definition ("a single reasonable indirect signal, not corroborated"), every fact this stage writes comes from exactly one uncorroborated X observation — never `CONFIRMED`/`STRONG_EVIDENCE`, regardless of how explicit the bio/tweet language is. Corroboration (multiple independent signal categories) is a later evidence-assembly stage's job, not this one's.

**Idempotency mechanism, documented.** `prospects` dedup relies on its existing `x_user_id`/`x_username` unique indexes (upsert-by-lookup, never a second insert). `prospect_sources`/`evidence`/`pain_signals` each get a cheap existence check (same prospect + same fixed fields) before insert, so re-running discovery against the same fixture does not accumulate unbounded duplicate rows — while still respecting `evidence`'s append-only design for genuinely *new* observations (e.g., a bio that changes between runs still appends a new fact rather than overwriting).

**Known limitation — handle reuse is not detected.** If an X username is reassigned from one account to a completely different one between two discovery runs, this stage's username-based lookup (used when no `x_user_id` is yet on file) would incorrectly treat the new account as the same prospect. Full protection would require either a schema change (a lifecycle/soft-delete concept on `prospects`) or a more complex reconciliation policy — neither implemented, since this is a rare edge case and the instructions ask to stop and report rather than invent a schema change speculatively.

**`searchUsers` (bio-targeted search) exists upstream but is not needed for this stage's pipeline.** Founder/CEO classification happens against the retrieved profile's bio (`getProfile`), not at search time — `searchTweets` (tweet-content search) is sufficient to surface candidates, since a person's own tweets frequently restate their role/business-model language anyway. `searchUsers` (X's "People" search product, which XActions also exposes) remains a reasonable future enhancement for more directly bio-targeted discovery, not a blocking gap for Stage 4B.

## 2C. Stage 4C Implementation Findings — Evidence Assembly, Technology Integration, and a Confirmed Scoring Gap

**Architecture.** `packages/prospecting/src/evidence-assembly/` connects Stage 4B's discovery evidence and Stage 2's technology detections to the unmodified Stage 3 scorer: `evidence-readers.ts` converts already-persisted `evidence`/`technology_detections` rows into Stage 3's exact `EvidenceFact[]`/`TriggerFact[]` input shapes (read-only, no new persistence); `evidence-assembly-service.ts`'s `EvidenceAssemblyService` orchestrates reuse-or-scan technology enrichment (via the existing `TechnologyEnrichmentService`, never `opentechalyzer` directly), calls the unmodified `normalizeEvidenceForScoring()` → `scoreProspect()`, and persists one `icp_scores` row per run. Zero schema changes — `icp_scores`' columns already matched `IcpScoreResult` exactly.

**Confirmed scoring gap: Revenue-Fit is currently unreachable from the automated pipeline for almost every real prospect.** Stage 2's `WATCHED_TECHNOLOGIES` list (`packages/adapters/src/open-tech-analyzer.adapter.ts`) does not include "Shopify Plus" as its own fingerprint — only plain "Shopify" is ever detected (RESEARCH.md §2A.7: not independently confirmed). Combined with Stage 4B never writing `employee_count_band`/`warehouse_fulfillment_signal` facts (no adapter supplies LinkedIn-style employee-count or job-posting-volume data) and the already-documented Revenue-Fit signal-4 contradiction (§16 of the Stage 4C brief; unchanged, not resolved here), **Revenue-Fit will read UNKNOWN (0 points) for essentially every prospect scored today**, unless a `confirmed_revenue_statement` evidence row is manually/independently supplied. This is a real, verified consequence of decisions already made and documented in Stage 1/2 (not a Stage 4C regression) — surfaced here explicitly because Stage 4C is the first point where the full pipeline actually runs end-to-end and the gap becomes externally visible in real scores, not just in code comments.

**Evidence-tier boundary explicitly regression-tested.** Per instruction, added tests proving a DB `evidence` row's own stored `evidence_tier` column (e.g., a row incorrectly tagged `CONFIRMED` at capture time) never changes Stage 3's own category-count-derived tier — `EvidenceFact` (the type `evidence-readers.ts` produces) structurally has no tier field at all, so the row's tier cannot reach the scorer even by accident; `readXEvidenceFacts` discards it explicitly and the discarding is unit-tested.

**Decision-maker sub-items intentionally left unpopulated.** `public_visibility` and `correct_profile_identified` (ICP §22.B, worth 4 and 3 points respectively) are never automatically derived by Stage 4B or Stage 4C — no current pipeline stage actually verifies "decision-maker has visible public activity" or "name/role/employer all confirmed" to the standard the ICP requires. Decision-maker scoring is therefore currently capped at the role-tier value alone (max 8, for `founder_or_ceo`) unless a future stage (or manual/independent evidence capture) populates these two facts.

**Trigger evidence remains structurally near-empty, by design.** `readTriggerFacts` is fully implemented and tested, but no current pipeline stage writes `trigger_signal` evidence rows at all (Stage 4B explicitly never does), so it returns an empty array in every real run today. This is intentional forward-compatibility, not a missed integration — building a trigger-evidence *source* was explicitly out of scope for both Stage 4B and Stage 4C per their own instructions (§14 of this stage's brief: "do not invent a trigger mapping").

**Golden scoring reproduced through the real assembly path, not just Stage 3's own unit tests.** Seeded realistic `evidence`/`technology_scans`/`technology_detections` rows and confirmed the full read→normalize→score pipeline reproduces the documented 63→C, 24→Reject, and a maximal 100→A total exactly — proving the assembly layer's category-to-fact mapping is correct, not just that Stage 3's arithmetic is correct in isolation (already proven in Stage 3's own test suite).

## 2D. Stage 5 Implementation Findings — Website Evidence Expansion, and Two Deliberate Non-Expansion Decisions

**Architecture.** `packages/prospecting/src/website-evidence/` adds exactly one new external read (a company's own public website, via a new `WebsiteReadAdapter` contract in `packages/core/src/adapters/website-read-adapter.ts` and its sole implementation, `WebsiteContentAdapter`, in `packages/adapters/src/website-content.adapter.ts` — Node's built-in `fetch`, zero new dependencies, kill-switch-gated, timeout-bounded, robots.txt-aware). `WebsiteEvidenceService` fetches a small fixed page set per domain (home/about/team/press/careers — configurable, capped at 4 pages by default via new `SystemConfig` keys), runs deterministic regex classifiers (`classifiers.ts`) over each page's extracted text, and writes facts into the *existing* `evidence` table using only the *already-defined* `SIGNAL_CATEGORIES`/`VALID_TRIGGER_TYPES` vocabulary from Stage 3's `evidence-normalization.ts` (untouched). Because Stage 4C's `evidence-readers.ts` already reads generically from `evidence` by category, none of Stage 4C's or Stage 3's code required any change for this new evidence to reach the scorer — confirmed by the full existing test suite (389 tests total after this stage) passing unchanged, including the golden 63/24/100/95/83 scoring reproductions.

**Closes two of Stage 4C's three documented gaps; the third is addressed partially.**
- **Revenue-Fit** — `employee_count_band` and `warehouse_fulfillment_signal` are now written from a company's own About/Team/Careers page text (an "equivalent" first-party source to the LinkedIn company page the ICP document names), and `confirmed_revenue_statement` is written when a page states an explicit first-party revenue figure with no funding/investment language nearby. Revenue-Fit is no longer unconditionally UNKNOWN — it now depends on what a given company's own website actually discloses, which for many real DTC brands will still be nothing, but the pipeline is no longer structurally incapable of finding it.
- **Decision-maker sub-items** — `correct_profile_identified` is now populated with zero new network I/O, by mining Stage 2's already-persisted `technology_scans.raw_response.enrichment.social.x` (OpenTechAnalyzer's own social-link extraction, fetched for an unrelated reason in Stage 2 and never read back out until now) against the prospect's X handle. `public_visibility` is now populated when a press/news page contains the decision-maker's full name near a quotation mark and an attribution verb ("said"/"told"/etc.) — a direct, conservative reading of the ICP's own "press quotes" language.
- **Trigger evidence** is populated for four of the six valid types (`new_product_launch`, `store_brand_expansion`, `funding_growth_announcement`, `funnel_offer_change`) from press/news page announcement language, each requiring a discrete, already-happened event phrase (never a "coming soon"/future-tense claim) and always sourced with that exact page's URL. `new_paid_channel_appearing` is deliberately NOT implemented — see below.

**Deliberate non-expansion decision 1: `new_paid_channel_appearing` from `technology_change_events`.** The database can represent dated technology-presence history (`technology_change_events.detected_at`), and it was tempting to treat a newly-`added` Meta Pixel/GA4 detection as "a new paid channel appearing." This was rejected: the ICP's trigger rule requires "a prior dated observation confirming its prior absence" of a *paid channel*, and a tracking-technology detection is not the same fact as active-ad-spend presence (the same distinction Stage 4C's `readTechnologyEvidenceFacts` already enforces for Maturity/Revenue-Fit — Meta Pixel ≠ paid acquisition). More or better-dated technology-scan history would never fix this; it is a fundamental evidence-type mismatch, not a coverage gap, so no code was written for it.

**Deliberate non-expansion decision 2: DTC/Business-Model-Fit evidence.** No new `dtc_signal.confirmed_dtc_with_owned_funnel` classifier was written. The ICP text requires "confirmed DTC/ecommerce model with owned acquisition funnel," and no deterministic, false-positive-free website-text pattern was found that reliably distinguishes "owns its funnel" from "is a Shopify storefront" or "sells DTC" in isolation — exactly the failure mode this stage's instructions warned against most heavily. Rather than ship a heuristic likely to misclassify wholesale-only or marketplace-only brands as DTC, this category is left to a future stage with a clearer, ICP-author-approved test.

**Paid Acquisition Activity/Intensity Fit is unchanged** — Stage 4B's job-posting matcher remains the only source, per instruction ("keep strict, no new categories"). No website-text pattern was found that maps cleanly to any of the ICP's four fixed categories (Meta/Google ad activity, a job posting, a named agency client) without stretching beyond what a company's own marketing copy can actually confirm.

**Network safety.** Every fetch is a single bounded HTTP GET per page (no link-following, no crawling), timeout-protected (default 8s, configurable), and gated by the same kill switch every other read/write adapter checks. `daily_limit_scrapes` (the existing shared scrape budget, already used by `DiscoveryService`) is reused for `WebsiteEvidenceService.runBatch` rather than inventing a second rate-limit mechanism — confirmed by a dedicated test that a batch stops with `budget_exhausted` once the shared limit is reached mid-run. robots.txt is fetched once per origin, cached in-memory for the adapter's lifetime, and a disallowed path is refused before the page itself is ever requested.

**Live network testing.** Not possible in this environment — this sandbox's egress policy blocks arbitrary outbound HTTP (confirmed via a direct `curl` test in an earlier stage of this build and re-confirmed as still true here). Every website-content/adapter test mocks `fetch` directly via the adapter's own `fetchImpl` injection point; no live website fetch was performed or is claimed.

## 2E. Stage 6A Implementation Findings — Outreach Foundation, Approval-Boundary Design, and One Documented Threshold Gap

**Architecture.** A new package, `packages/outreach/`, implements the foundation of `Qualified Prospect -> Outreach Eligibility -> Personalization Evidence -> Message Draft -> Human Approval` — and stops there. It depends only on `@metrivio/core` (no dependency on `@metrivio/prospecting` or `@metrivio/adapters`), reads `prospects`/`icp_scores`/`conversations`/`evidence`/`pain_signals`/`technology_detections` rows that already exist, and writes nothing except new `audit_log` rows. `packages/core/src/scoring/` is neither imported nor modified — eligibility reads a prospect's latest `icp_scores.tier` as one input among several, but the tier itself is never recomputed, and no scoring weight/multiplier/band/exclusion was touched.

**Outreach score threshold — genuinely undefined, left unresolved rather than invented (Section B).** Neither `docs/01-metrivio-offer.md` nor `docs/02-metrivio-icp.md` defines a score/tier cutoff for when a prospect should actually be contacted — the ICP score bands (§22.C) are fit bands, not a contact policy. A new `system_config` key, `outreach.minimum_tier`, was added with **no seeded default** (unlike every other config key in `system-config.ts`, this one is deliberately absent from `seedDefaultsFromEnv`): `getOutreachMinimumTier()` returns `null` until a human sets it explicitly, and the eligibility evaluator treats `null` as INELIGIBLE for every prospect — a fail-closed default, consistent with this codebase's existing "unset config = safest state" convention (daily limits default to 0, automation mode defaults to `dry_run`).

**Eligibility is a pure function; the seven statuses are checked in a fixed, most-definitive-first order.** `evaluateOutreachEligibility()` (`eligibility.ts`) takes already-gathered facts (outreach status, latest score, latest conversation, evidence presence, kill switch, configured threshold) and returns exactly one of ELIGIBLE/INELIGIBLE/BLOCKED/ALREADY_CONTACTED/AWAITING_REPLY/STOPPED/UNKNOWN — never a boolean. Order: STOPPED (terminal opt-out/stop states, and a conversation classified OPT_OUT/NOT_INTERESTED) is checked first and overrides everything, including the kill switch; then BLOCKED (kill switch); then AWAITING_REPLY/ALREADY_CONTACTED (already engaged); then UNKNOWN (no score yet) vs. INELIGIBLE (score exists but excluded/Reject/below threshold/no evidence); ELIGIBLE only if every check passes. The I/O layer (`eligibility-service.ts`) gathers these facts from real tables and performs zero writes.

**Message-draft state machine is deliberately 4 states, not the ~13 the prompt listed as possibilities.** DISCOVERED/ENRICHED/SCORED/OUTREACH_ELIGIBLE/STOPPED/OPTED_OUT already exist as observable facts elsewhere (a `prospects`/`icp_scores` row, an eligibility read, `prospects.outreach_status`); SENT/AWAITING_REPLY/REPLIED/FOLLOWUP_DUE/FAILED all require an actual send, which this stage does not build. The one genuinely new object is a `MessageDraft`, whose lifecycle is DRAFTED -> PENDING_APPROVAL -> {APPROVED | REJECTED} (DRAFTED can also go straight to REJECTED). There is no `SEND` transition defined anywhere in the transition table — `APPROVED -> SENT` is not merely undocumented, it does not exist as code. A duplicate transition into the same state (e.g. approving an already-APPROVED draft) is idempotent (no-op, no new audit row); any other invalid transition throws `InvalidDraftTransitionError`.

**Message drafts and their approval history live entirely in the existing `audit_log` table — zero schema changes.** `outreach_messages` (DATABASE.md §2) was evaluated and found insufficient to represent DRAFTED/PENDING_APPROVAL/APPROVED/REJECTED without a migration: its `status` enum is `queued`/`sent`/`failed`/`skipped_stop_condition` and its `sequence_id`/`sequence_step_order` columns are `NOT NULL`, i.e. it models a message already committed to a running sequence, with no approval-workflow columns (`approval_status`, `rejection_reason`) at all. Per Section N, this is documented rather than silently migrated. The alternative implemented instead: `OutreachDraftService` writes one `audit_log` row per lifecycle event (`entity_type = 'outreach_draft'`, `entity_id = <draft id>`, `detail` carrying the draft snapshot or transition metadata plus an explicit monotonic `sequence` number), and a draft's current state is reconstructed by replaying its own rows in `sequence` order — this is a direct application of DATABASE.md's own stated principle ("nothing is deleted, only superseded... so the audit trail stays intact"), not a new mechanism. **Known limitation, not fixed here:** `listDraftsForProspect` scans every `outreach.draft.created` row and filters by prospect id in application code (no index) — acceptable at this stage's scope; if draft volume grows, a real `message_drafts` table (or an index) would be the correct fix, not a workaround bolted onto the audit-log approach.

**Personalization only ever restates a row that already exists.** `buildPersonalizationCandidates()` reacts to a small, explicit allowlist of `(evidenceType, signalCategory)` pairs already defined by Stage 3's own `SIGNAL_CATEGORIES`/`VALID_TRIGGER_TYPES` (imported, never redefined) plus `technology_detections`/`pain_signals` rows — an evidence row outside that allowlist produces zero candidates, not a guessed one. Confidence is derived mechanically from the row's own stored `evidence_tier` (`CONFIRMED` -> `FACT`, anything else -> `INFERENCE`; `pain_signals` rows, which carry no tier column, are always `INFERENCE`) — this module does not invent its own tier-to-confidence table per category. Adversarial tests specifically verify: a detected technology (Shopify, Meta Pixel) never produces a DTC or paid-acquisition-shaped candidate; an unsourced or invalid-type trigger produces nothing; an unrecognized `signalCategory` (including a syntactically valid-looking but unlisted one) produces nothing; a `confirmed_spend_statement` row's actual dollar figure is never present in the candidate's `observation` text (the figure stays in the evidence row's own `raw_value` for a human to see, never auto-surfaced). Revenue was deliberately excluded from the five hook categories entirely (not just gated) — ICP §22's revenue-disclosure hard rule is high-stakes enough that Stage 6A avoids building a revenue-shaped hook at all rather than trusting a gate to hold perfectly in every future template.

**Message templates never splice raw scraped text into outreach copy.** `renderMessageDraft()` re-phrases every hook category through a fixed template — even a `safeToStateAsFact: true` candidate's literal `observation`/`rawValue` text is never inserted verbatim, only its category. This is a deliberately more conservative choice than the ICP document strictly requires (which would permit stating a CONFIRMED revenue/spend figure) — the reasoning: a template system is not the right place to decide a scraped sentence reads naturally and isn't misleading once spliced in; a human reviewer editing the draft before approval is. This can be revisited in a later stage once an LLM-assisted or human-authored personalization path exists.

**Future X write interface — no new interface created.** Section H asked for "a future interface such as `XOutreachAdapter`... implementation absent/stubbed." `packages/core/src/adapters/x-write-adapter.ts`'s `XWriteAdapter` (Stage 1) already is exactly this — `postTweet`/`postThread`/`sendDM`/`replyTo` are already defined, and both existing implementations (`XActionsWriteAdapter`, `XManagerWriteAdapter`) still throw `NotImplementedInStage1Error` on every method, unchanged since Stage 1. Inventing a second, parallel interface for the same eventual responsibility was judged worse than reusing the existing one — confirmed via `git diff` that neither adapter file nor `x-write-adapter.ts` has any diff from this stage.

**Follow-up / reply-detection — no schema gap found (Section I/J).** `sequences.steps[].day_offset` + `outreach_messages.sent_at` + the existing `(prospect_id, sequence_id, sequence_step_order)` unique constraint already fully represent follow-up timing/dedup; `conversations.last_message_direction`/`classification` and `conversation_messages.direction` already represent reply-detected/stopped/opted-out. `packages/outreach/src/follow-up/contracts.ts` defines `FollowUpEligibilityInput`/`FollowUpEligibilityResult`/`ReplyDetector` as pure types for a future stage to implement against — no class implements `ReplyDetector` anywhere in this package, and no scheduling/polling logic exists.

## 2F. Stage 6B — X Write / Send

**Write capability: verified-absent, not implemented, and not faked.** Before writing any send code, this stage's own instructions required inspecting the vendored XActions subtree (`packages/adapters/vendor/xactions-http/`) for a reusable DM-send implementation. The finding is unambiguous and was already on record from Stage 4A: `VENDOR.md`'s own "Deliberately NOT vendored" list names `dm.js` explicitly, alongside `actions.js`/`engagement.js`/`media.js`, as a write/mutation path excluded from the read-only subtree. `endpoints.js` (vendored wholesale only because `client.js`/`profile.js`/`search.js`/`tweets.js` share it as a config module) happens to carry the bare REST path string `REST.dmNew = '/1.1/dm/new2.json'`, and `RATE_LIMITS.dmNew` — but a path string and a rate-limit budget are not a request format. The actual JSON/form body shape X's DM-send endpoint requires was never vendored, so it is not verified anywhere in this codebase. Per instruction, that gap is not closed by invention: `XActionsSendAdapter.sendDirectMessage()` (`packages/adapters/src/xactions-send.adapter.ts`) performs the kill-switch check and the authentication precondition for real, then throws `XSendUnexpectedError` with a message naming the exact gap — it never constructs a speculative request, never silently no-ops as if it succeeded, and never fabricates a response. **No dependency was added to close this gap** (no XActions npm install, no Puppeteer/Playwright/browser automation) — none of those were judged necessary; the honest answer is "the request format needs to be sourced from verified upstream code or documentation before this can be implemented safely," not "a bigger toolchain is needed." Whether a future stage should be created specifically to source and verify that format (e.g. by vendoring `dm.js` itself after the same commit-pin/file-list scrutiny `VENDOR.md` already applies) is exactly the kind of decision this section defers to the founder rather than resolving unilaterally.

**Architecture.** `SendApprovedDraftService` (`packages/outreach/src/send/send-service.ts`) is the entire `APPROVED DRAFT -> SAFE SINGLE X SEND -> AUDIT/RESULT` boundary — one public method, `send(draftId, prospectId, dryRun?)`, no batch/bulk variant, no scheduler, no queue worker. It depends on `OutreachDraftService` (Stage 6A, unmodified) to reload a draft's authoritative current state and on a new, narrow `XSendAdapter` contract (`packages/core/src/adapters/x-send-adapter.ts`) for the one send operation. `XSendAdapter` is a **new, separate interface**, not an extension of Stage 1's `XWriteAdapter` — widening `XWriteAdapter.sendDM(handle, ...)` would have (a) required a username-based signature this stage's own instructions reject ("must use the canonical X user ID... do not rely solely on username") and (b) forced `XActionsWriteAdapter`/`XManagerWriteAdapter` to grow a method neither needs, breaking their zero-diff status since Stage 1. `git diff` confirms `x-write-adapter.ts` and both its implementations are untouched by this stage.

**Authentication model.** Follows the verified mechanism already in `TwitterHttpClient` (Stage 4A) exactly — a cookie string (`auth_token=...; ct0=...`) sourced by the caller from the existing `credentials` table's encryption-at-rest pattern, never read from an environment variable inline. `isAuthenticated()` (already exposed by the vendored client) is checked before anything else send-specific: DM sending has no guest-mode equivalent on X (unlike the read-only profile/search paths), so a missing/invalid session throws `XSendAuthenticationRequiredError` — mapped to `AUTH_REQUIRED` — before the capability-gap error is ever reached. No credential value appears in any thrown error's message (regression-tested directly) or in any audit_log row (the send service only ever passes ids/outcomes/reasons to `writeAuditLog`, which itself already refuses a payload containing a credential-shaped key per RISK_REGISTER.md #9's existing control).

**Target identity (Section C).** The send service reloads the prospect row fresh at send time (never trusts a caller-supplied object) and requires `prospects.x_user_id` (the canonical, immutable X-assigned ID) to be non-null — a prospect enriched only far enough to have a username is `TARGET_INVALID`, never sent to via fuzzy/username-only matching. The draft's own `prospectId` is cross-checked against the caller's stated target prospect id, catching a mismatched draft/prospect pair before anything else.

**Approval enforcement (Section D).** `OutreachDraftService.getDraft()` is called fresh on every `send()` invocation — never a cached/stale object — and only `status === 'APPROVED'` proceeds; `DRAFTED`, `PENDING_APPROVAL`, `REJECTED`, and a missing/unknown draft id all resolve to `NOT_APPROVED`. There is no approval-expiry concept anywhere in the existing schema/Stage 6A design to check, so none was invented.

**Duplicate-send protection (Section F) — reuses, does not reinvent, existing schema.** `outreach_messages`' own `(prospect_id, sequence_id, sequence_step_order)` unique index (DATABASE.md §5.4's documented "hard backstop against duplicate sends across restarts") is the actual mechanism: `packages/outreach/src/send/manual-sequence.ts` lazily creates one well-known, genuinely single-step `sequences` row (`stage_6b_manual_send`) and every Stage 6B send always addresses step 1 of it — meaning a prospect can receive at most one Stage 6B send, ever, which is the *correct* behavior for a stage that explicitly excludes follow-ups, not an accidental side effect. Before attempting a send, the service looks up any existing row for that (prospect, sequence, step): a `sent` row is `ALREADY_SENT`; a `failed` row whose recorded `error_detail` marks it `ambiguous: true` (a real network failure whose delivery status to X is unknown) is *also* `ALREADY_SENT` — a deliberately conservative choice, since a second attempt could double-send if the first one actually landed, and this codebase has no way to check X's own delivery state; a `failed` row that is *not* ambiguous (e.g. this exact documented capability gap, which by construction never reached the network) may be retried by an explicit, human-initiated call — never automatically. `personalization_basis` (an existing nullable JSON column, documented as "which evidence row(s) the personalization referenced") additionally carries `{draftId, evidenceReferences}` so the exact draft behind any `outreach_messages` row is always traceable.

**Kill switch (Section G).** Checked twice with the existing `KillSwitch` class, unchanged: once before any draft/prospect/message work begins ("before preparing the write"), and again immediately before the line that would call `sendAdapter.sendDirectMessage()` ("immediately before the network write") — both regression-tested, including that a switch flipped on between the two checks still blocks the second one. No parallel kill-switch mechanism was created.

**Rate/daily limits (Section H).** Reuses the existing `daily_limit_dms` `system_config` key (Stage 1) — Section H explicitly asks to determine what already exists before adding anything, and this key already exists for exactly this purpose, so no new rate-limit key was added. The count itself is a rolling 24-hour count of `outreach_messages` rows with `channel = 'dm'` and `status = 'sent'`, computed at send time (not a separately-tracked counter that could drift from reality). One genuinely new key was added: `outreach.max_message_length` (Section J, message validation, not a rate limit) — no existing key represents a per-message length bound, and the ICP/offer documents say nothing about it, so a deliberately conservative default (500 characters) was chosen and documented as **not** a verified X platform limit (that number is not obtainable from this codebase's vendored source either, for the same `dm.js`-exclusion reason above) — a safety default for a cold-outreach message, pending real verification.

**Dry-run (Section I).** Every check above (kill switch ×2, approval, target identity, message validation, duplicates, limits) runs identically in dry-run mode; the only difference is that the function returns before calling `sendAdapter.sendDirectMessage()` and before writing any `outreach_messages`/`conversations`/`conversation_messages` row — regression-tested directly (`never creates a fake SENT/outreach_messages row`). The result includes the resolved canonical `xUserId`/`xUsername` and the exact message text that would have been sent (safe — no credential material is ever part of this payload) so an operator can verify correctness before actually approving a real send.

**Content safety / claim boundary (Section K).** The send service never reads, edits, regenerates, or personalizes the draft's `messageText` — it is passed to `sendAdapter.sendDirectMessage()` and written to `outreach_messages.message_content`/`conversation_messages.content` byte-for-byte as reloaded from the approved draft. No LLM call exists anywhere in this stage's code.

**Audit logging (Section M).** Every `send()` call — regardless of outcome, including `BLOCKED`/`DRY_RUN`/every rejection — writes exactly one `audit_log` row (`action_type = 'outreach.send.attempt'`, `entity_type = 'outreach_message'`) via the existing `writeAuditLog()` helper (unchanged), which already refuses a payload containing a credential-shaped key. `detail` carries only `{draftId, prospectId, outcome, reason}` — never the message text itself (kept out deliberately, consistent with instruction M's "do not store message text in audit logs unless the existing audit architecture explicitly requires it"; the message text is already durably stored in `outreach_messages`/`conversation_messages` on an actual send, so nothing is lost by keeping it out of the audit row).

**Persistence behavior (Section N/O) — zero schema changes.** `outreach_messages` was evaluated field-by-field against what Section N asks it to represent: approved message ✓ (`message_content`), send attempt/result ✓ (`status`: `sent`/`failed`), sent timestamp ✓ (`sent_at`), draft provenance ✓ (`personalization_basis`, reused as described above). The one field Section N specifically calls out — "X message identifier if available" — is **not** a column on `outreach_messages` (and none was added); it is already a column on `conversation_messages.x_message_id` (DATABASE.md §2), which this service also writes on a successful send, alongside finding-or-creating a `conversations` row (`state = 'active'`, `last_message_direction = 'outbound'`) per Section O. Together, the three existing tables fully cover Section N/O's requirements with no migration.

**Error handling (Section P).** `SendApprovedDraftService` performs the adapter call exactly once per `send()` invocation — there is no retry loop anywhere in this file. A failed attempt's `error_detail` records an explicit `ambiguous: true/false` flag (network-shaped failures are `true`; auth/rate-limit/not-found/the documented capability gap are all `false`, since their cause is precisely known and nothing was transmitted) so a human operator — or a future stage — can tell whether a resend risks a double-send.

**Testing.** 45 new tests: `xactions-send.adapter.test.ts` (5 — kill switch, auth precondition, the capability-gap error, no credential leakage, check ordering), `send-service.test.ts` (37 — approval enforcement, target identity, duplicate protection including the ambiguous-vs-non-ambiguous retry distinction, kill switch ×2, limits at/below/above the boundary, dry-run, message validation, exact-text preservation, every error-mapping branch, audit logging including "no secrets," conversation persistence, and a direct "no batch/bulk/scheduler/queue/retry method exists" regression check), `manual-sequence.test.ts` (3). Full suite: 529/529 passing, including the unchanged golden scores (63→C, 24→Reject, 100→A, 95→A, 83→B) and every prior stage's test file untouched.

**Live X testing status.** Not performed and not claimed. No live authenticated X write occurred or could occur in this environment (egress policy blocks arbitrary outbound HTTP, confirmed in earlier stages) — and independent of that sandbox constraint, `XActionsSendAdapter` never reaches a real network call at all yet (see the write-capability finding above), so there is nothing live to test even in an unrestricted environment until a future stage closes the request-format gap.

**Known limitations.** (1) The core send capability itself is not implemented — this is the headline finding of this stage, not a footnote; every safety mechanism around it (approval, identity, duplicates, limits, kill switch, dry-run, audit) is real and tested, but `SendApprovedDraftService.send()` cannot currently deliver a real DM. (2) The message-length default (500 characters) and the ambiguous/non-ambiguous retry split are this codebase's own conservative policy choices, not verified X platform behavior. (3) `outreach_messages`' unique index caps Stage 6B at one send per prospect for the lifetime of the `stage_6b_manual_send` sequence row — correct for this stage's explicit no-follow-ups scope, but a future multi-step sequence engine (BUILD_PLAN.md Stage 8) will need its own step-addressing, not an extension of this one row.

## 2H. Stage 6C — Reply Detection / Follow-Up Eligibility Foundation

**Architecture.** `X conversation/reply detection -> outreach state update -> follow-up eligibility calculation`, with a hard boundary at the end: nothing in this stage sends, schedules, or queues a follow-up. `ReplyDetectionService` (`packages/outreach/src/follow-up/reply-detection-service.ts`) is entirely read-only — it never imports or calls `XSendAdapter`/`SendApprovedDraftService`. `FollowUpEligibilityService`/`evaluateFollowUpEligibility()` only ever answer the eligibility question; there is no `sendFollowUp`, `sendNextStep`, batch-send, scheduler, or autonomous-worker method anywhere in this package — confirmed by `git diff` showing zero diff on `packages/outreach/src/send/` and by grep sweep finding no reference to `XSendAdapter` outside doc comments explaining its absence.

**Verified X read capability.** Following the same discipline Stage 6B-R established (re-clone the already-pinned commit, verify against upstream's own code and test assertions, vendor only what's used), this stage re-inspected upstream `dm.js`'s `getInbox()`/`getConversation()` — both real, tested functions (`describe('getInbox()', ...)`/`describe('getConversation()', ...)` in `tests/http-scraper/dm.test.js`), previously deliberately excluded from the vendored excerpt because Stage 6B-R's scope was send-only. Both are now vendored (trimmed, alongside their parsing helpers `parseInboxState`/`parseConversationData`/`parseReactions`), verified request URL/response shape by URL, and error behavior identical to `sendDM`'s (same `client.request()`, same error classification). `XActionsReplyDetectorAdapter.getConversationMessages(targetUserId)` resolves the X-native conversation by scanning the first page of `getInbox()` for a `one_to_one` conversation containing that canonical user ID as a participant, then fetches its messages via `getConversation()` — bounded (one page, no pagination loop), never an unbounded crawl.

**Identity handling (Section B).** `classifyMessageDirection()` (`reply-direction.ts`) compares only canonical X user IDs — `senderXUserId` against `prospects.x_user_id` — never a username, display name, message text, or position in the message list. It returns exactly two outcomes: `'prospect'` on an exact ID match, `'unknown'` for everything else, including a missing ID on either side. Deliberately, it never returns an "ours" classification by exclusion (i.e., "not the prospect, so it must be us") — this codebase has no independently verified "our own account's X user ID" configured anywhere, and inferring direction from absence of a match would be exactly the unsafe inference this stage's instructions forbid. Because `conversation_messages.direction` only accepts `'outbound'`/`'inbound'` (no `'unknown'` value in that column's enum), `ReplyDetectionService` never writes a row for a message it can't positively attribute to the prospect — outbound messages are already recorded firsthand by Stage 6B's own send flow, from actual knowledge, never inferred here.

**Conversation mapping (Section C) — no schema gap, resolved dynamically instead of migrated.** DATABASE.md's `conversations` table has no `x_conversation_id` column. Rather than adding one, the X-native conversation ID is resolved fresh on every detection call via `getInbox()`'s participant list (see above) — this makes a persisted column unnecessary, not merely avoidable. `conversations`/`conversation_messages`/`outreach_messages` are otherwise used exactly as documented, with zero new tables or columns.

**Reply state (Section D).** `deriveReplyState()` (`reply-state.ts`) produces exactly one of `NO_REPLY`/`REPLIED`/`UNKNOWN`/`STOPPED`/`OPTED_OUT`, checked in that priority order (most specific first: `OPTED_OUT` > `STOPPED` > `REPLIED` > `NO_REPLY`, with `UNKNOWN` forced whenever the detection attempt itself did not succeed — a failed/blocked network call, or a prospect with no canonical X user ID on file). `UNKNOWN` is never collapsed into `NO_REPLY` anywhere in this module — regression-tested directly (`reply-state.test.ts`: "never collapses UNKNOWN into NO_REPLY").

**Opt-out detection (Section E).** `classifyOptOutIntent()` (`opt-out-classifier.ts`) is a deterministic, whole-phrase regex matcher — no LLM anywhere in this stage. Eleven explicit no-further-contact phrase patterns (stop contacting/messaging/emailing/texting me, do not contact/message/email me, remove me from your list, take me off your list, unsubscribe, "not interested, don't follow up", leave me alone, no more messages) — each requiring the full phrase, never a bare keyword ("stop"/"remove" alone never match). Ordinary rejection ("not interested" alone, "no thanks", "maybe later") is explicitly regression-tested as NOT an opt-out — it remains available for the existing, separate `conversations.classification = 'NOT_INTERESTED'` value, which this stage does not otherwise touch.

**Follow-up eligibility (Section F) — 8 statuses, one critical invariant.** `evaluateFollowUpEligibility()` (`follow-up-eligibility.ts`) is a pure function producing `ELIGIBLE`/`NOT_DUE`/`REPLIED`/`STOPPED`/`OPTED_OUT`/`UNKNOWN`/`ALREADY_SENT`/`BLOCKED`. **Critical invariant (Section H), directly regression-tested with 7 dedicated cases:** once `replyState` is `REPLIED` or `OPTED_OUT`, the function returns that status unconditionally — before any timing math runs at all — regardless of how due, overdue, or exactly-at-boundary the timing input says a follow-up would otherwise be. `FollowUpEligibilityService` enforces this at the I/O layer too: it always runs a *fresh* `ReplyDetectionService.detectReplies()` check before computing eligibility (never trusting stale stored state), so a reply detected one second ago is guaranteed to block a follow-up eligibility check made right after.

**Sequence timing (Section G).** Reuses `sequences.steps[].day_offset` exactly as already defined — no second scheduling model. `FollowUpEligibilityService` finds the most recent `sent` `outreach_messages` row for the (prospect, sequence) pair, looks up the next `step_order`'s definition in `sequences.steps`, and computes `dueAt = lastSentAt + day_offset days`. When no prior sent message exists, or no next-step definition exists in `sequences.steps`, the result is `UNKNOWN` (never an invented default timing) — distinct from `NOT_DUE`, which only applies once a real day_offset genuinely hasn't elapsed yet.

**Idempotency / duplicate detection (Section I).** `ReplyDetectionService` dedups strictly by X's own `x_message_id` (`conversation_messages.x_message_id`) — an observed message whose ID already exists on a row for that conversation is never re-inserted, regression-tested directly ("processing the same X message ID twice never creates a duplicate row"). **Known limitation, documented rather than worked around:** if an upstream response ever omits a message's ID (the vendored parser defaults to `''` in that case), this codebase does not treat two ID-less observations as reliably distinguishable — it does not fabricate identity for them, and a caller relying on this path should not assume dedup works for that edge case. In practice, both `getConversation()`'s own upstream fixtures and this project's testing show DM message IDs are consistently present; this is a documented theoretical limitation, not an observed failure.

**Kill switch (Section K).** Checked at three layers, all reusing the existing unmodified `KillSwitch` class: inside `XActionsReplyDetectorAdapter` (before any network call), at the start of `ReplyDetectionService.detectReplies()` (before even attempting network work, for a prospect not already resolved as stopped), and at the start of `FollowUpEligibilityService.evaluate()` (before it would even call reply detection). A kill-switch-active reply detection always resolves to `replyState: 'UNKNOWN'` — never `NO_REPLY` — and a kill-switch-active eligibility check always resolves to `BLOCKED`, a status distinct from every other outcome, regression-tested directly.

**Rate limits (Section L).** No new rate-limit key was added. `ReplyDetectionService.detectRepliesBatch()` reuses the existing `daily_limit_scrapes` config and the existing `JobRunner` mechanism exactly like `WebsiteEvidenceService.runBatch`/`DiscoveryService.run` — one budget unit is charged only when a real network call was actually attempted (a prospect resolved as already-stopped, kill-switch-blocked, or missing a canonical X user ID costs nothing, tracked via an internal `networkCallAttempted` flag rather than inferred from the result shape).

**Audit/provenance (Section M).** Every `detectReplies()` call — success, failure, or any early-exit branch — writes exactly one `audit_log` row (`action_type = 'outreach.reply_detection.checked'`) via the existing `writeAuditLog()` helper (unchanged, already refuses credential-shaped payload keys). `detail` carries only `{prospectId, conversationId, replyState, newMessagesFound, detectionSucceeded}` — never message content, regression-tested directly. Message content itself is preserved with full provenance in `conversation_messages` (`x_message_id`, `content`, `timestamp`), exactly like Stage 6B's own outbound-message recording.

Full suite: 632/632 passing, golden scores (63→C, 24→Reject, 100→A, 95→A, 83→B) unchanged.

**Live X testing status.** Not performed and not claimed. Every adapter test injects a fake `TwitterHttpClient`-shaped object via the same `client` constructor-injection escape hatch established in Stage 6B/6B-R; no test in this repository calls `fetch`/the real vendored `client.request()` against x.com. This environment's egress policy blocks arbitrary outbound HTTP regardless (re-confirmed as still true).

**Known limitations.** (1) `getInbox()` is only read for its first page (the vendored default limit) — a prospect whose 1:1 conversation falls outside that page in an account with a very large number of DM threads would resolve as "no conversation found," which is functionally indistinguishable from "no conversation exists yet" in the current design; a future stage adding pagination would need to walk `getInbox()`'s `cursor` explicitly. (2) Message-ID-less dedup is a theoretical gap only (see Section I finding above). (3) `FollowUpEligibilityService.evaluate()` always triggers a fresh reply-detection network call rather than reading only already-stored state — a deliberate choice favoring correctness (Section H's invariant) over minimizing X read volume; a future stage could relax this with an explicit "max staleness" parameter if read volume becomes a concern. (4) No "our own account's X user ID" is configured anywhere in this codebase, so this stage cannot positively confirm which non-prospect messages are genuinely outbound from our own account versus some other unexpected sender — it simply never needs to make that distinction, since only prospect-attributed messages matter for reply detection.

## 2I. Stage 6D — Follow-Up Execution Foundation

**Architecture.** `Follow-up Eligibility -> Follow-up Personalization -> Follow-up Draft -> Human Approval -> Safe Single X Send`, built entirely as an extension of the two systems Stage 6A/6B/6C already established rather than a parallel one: `FollowUpDraftService` (`packages/outreach/src/follow-up/follow-up-draft-service.ts`) is the only new orchestrator, and it delegates drafting to the same `OutreachDraftService`/audit-log-backed draft state machine Stage 6A built, and sending to the same `SendApprovedDraftService` Stage 6B built. No new table, no new approval mechanism, no new send mechanism, no scheduler, no queue, no autonomous execution path exists anywhere in this stage's diff — `git diff --stat` on `packages/outreach/src` shows only edits to existing Stage 6A/6B/6C files plus four genuinely new files (`sequence-step.ts`, `follow-up-message-templates.ts`, `follow-up-draft-service.ts`, and this stage's test files).

**Eligibility integration (Section B) — zero duplicated timing logic.** `FollowUpDraftService.generateFollowUpDraft()` calls `FollowUpEligibilityService.evaluate()` (Stage 6C, unchanged in its own eligibility contract) first, and only proceeds to draft when the result is exactly `ELIGIBLE`. Every other status (`NOT_DUE`/`REPLIED`/`STOPPED`/`OPTED_OUT`/`UNKNOWN`/`ALREADY_SENT`/`BLOCKED`) is returned as-is, with drafting refused. A shared read-only helper, `findNextSequenceStep()` (`sequence-step.ts`), was extracted from Stage 6C's `FollowUpEligibilityService` (which previously computed "what's the next step" inline) so that `FollowUpDraftService` can also learn the next step number/day-offset/whether-a-next-step-exists without a second, drifting copy of that lookup — the actual due/not-due timing *math* itself still lives solely in Stage 6C's `evaluateFollowUpEligibility()`, never duplicated. This refactor was verified behavior-preserving by re-running Stage 6C's existing 80 follow-up tests unchanged before writing any Stage 6D code, and again in the final full suite.

**`NO_NEXT_STEP` (Section F) — a Stage-6D-local distinction, not a change to Stage 6C's contract.** Stage 6C's `evaluateFollowUpEligibility()` still returns a single `UNKNOWN` status for every "timing couldn't be determined" cause (no prior sent message at all, no next-step definition, or a genuinely undetermined reply state) — its own tested contract is untouched. When `FollowUpDraftService` sees `UNKNOWN`, it separately consults `findNextSequenceStep()` to check specifically for the "a prior step was sent, but `sequences.steps` defines nothing after it" case, and reports that one case as `NO_NEXT_STEP` instead of the generic `UNKNOWN` — every other `UNKNOWN` cause (no prior send yet, a failed reply-detection network call) is still reported as `UNKNOWN`, unchanged.

**Follow-up draft contract (Section A).** `MessageDraft` gained four optional fields — `sequenceId`, `sequenceStepOrder`, `parentOutreachMessageId`, `followUpIntent` — all `undefined` for an original Stage 6A/6B-shaped draft (every existing caller/test that never sets them is unaffected; confirmed by the full unmodified Stage 6A/6B/6C suites passing unchanged). `GenerateDraftInput` gained one optional `followUp` block carrying the same fields plus `excludeEvidenceId`; `OutreachDraftService.generateDraft()` branches on its presence to render via the new follow-up templates and exclude the original hook's evidence, but is otherwise the exact same method, same audit-log persistence, same idempotency rule (at most one non-terminal draft per prospect, regardless of original vs. follow-up) — deliberately not a second `generateFollowUpDraft` method, since that would have duplicated ~90% of the existing method's body.

**Reply recheck (Section C) — "Draft generated != Follow-up still eligible".** `SendApprovedDraftService` gained one new, entirely optional constructor parameter: `followUpEligibilityService?: FollowUpEligibilityService`. When present, and only when the reloaded draft itself carries a `sequenceId` (i.e., it is a follow-up draft), `send()` re-runs `FollowUpEligibilityService.evaluate()` — which itself always re-runs live reply detection, per Stage 6C's own invariant — immediately before the message-validation/duplicate/limit checks and the network write, never trusting the eligibility result that existed back when the draft was generated. A non-`ELIGIBLE` recheck result blocks the send outright, mapped to one of five new, semantically distinct outcomes (below) — the draft is never re-drafted, retried, or silently downgraded. When the dependency is omitted, or the draft has no `sequenceId` (every original Stage 6A/6B-shaped draft), `send()`'s behavior is byte-for-byte identical to Stage 6B — verified by all 37 pre-existing `send-service.test.ts` tests passing completely unmodified.

**New send outcomes (Section C/M) — never conflated with `BLOCKED`'s kill-switch-only meaning.** `OutreachSendOutcome` gained `REPLIED`, `OPTED_OUT`, `STOPPED`, `NOT_DUE`, and `FOLLOW_UP_INELIGIBLE` (a catch-all for a recheck landing on `UNKNOWN` or `ALREADY_SENT` immediately before send). `BLOCKED` is reserved, exactly as Stage 6B defined it, for "the kill switch is active" — including when the *eligibility* recheck itself is the one reporting `BLOCKED` (since Stage 6C's own `BLOCKED` status is defined identically), so this invariant from Stage 6B carries through unchanged rather than being overloaded.

**Duplicate protection (Section I) — the dedup key now resolves from the draft, not a hardcoded singleton.** Stage 6B's `send()` previously always used the `stage_6b_manual_send` singleton sequence + step 1 as the `outreach_messages` dedup key, which was correct only because Stage 6B never sent more than one message per prospect. A follow-up genuinely needs its own real `(sequenceId, sequenceStepOrder)` as the key — `send()` now resolves `sequenceId = draft.sequenceId ?? (manual-send singleton)` and `sequenceStepOrder = draft.sequenceStepOrder ?? MANUAL_SEND_STEP_ORDER`, so an original draft's behavior is completely unchanged (it still hits the singleton) while a follow-up's dedup, insert, and update all key off its own sequence step. `outreach_messages`' existing `(prospect_id, sequence_id, sequence_step_order)` unique index remains the single source of truth for this — no new uniqueness mechanism, and a repeated send attempt at the same follow-up step is regression-tested directly (`send-service-follow-up.test.ts`: "never sends the same prospect+sequence+step twice").

**Follow-up personalization (Section D).** `DraftGenerationService.gatherPersonalizationInputs()` was extracted from the existing `generateDraftForProspect()` (identical queries, zero behavior change — verified by the 5 pre-existing `draft-generation-service.test.ts` tests passing unmodified) so `FollowUpDraftService` reuses the exact same evidence/pain-signal/technology-detection gathering rather than a second implementation. The follow-up's candidate pool excludes the original message's `selectedHook.evidenceId` (resolved by reading the original `outreach_messages` row's `personalizationBasis.draftId` and looking up that draft's own `selectedHook`), so a follow-up is structurally required to surface a genuinely different verified observation when one exists, and falls back to a value-oriented, fact-free clause when none does — never inventing one. `renderFollowUpMessageDraft()` (`follow-up-message-templates.ts`) mirrors `renderMessageDraft()`'s existing discipline exactly: fixed deterministic templates, category-level paraphrase only, no raw scraped text ever spliced in, no dollar/ROAS/CAC/headcount figures, and explicitly never "just following up" or "I know you're busy" as the message's only content — regression-tested directly.

**Message strategy (Section E) — three intents, deterministic templates.** `clarification` (first follow-up), `reminder` (a subsequent, non-final follow-up), `final_close` (the sequence's last defined step) — chosen by `FollowUpDraftService` purely from the resolved next step's position (`nextStepOrder`) and whether it is the sequence's last defined step (`isLastStep`, computed by `findNextSequenceStep()`), never re-deriving timing. No LLM is used. Each intent's rendered text is guaranteed distinct from the other two and from the original message's own template output — regression-tested directly (`follow-up-message-templates.test.ts`).

**Human approval (Section G) / Send integration (Section H).** A follow-up draft goes through the identical `DRAFTED -> PENDING_APPROVAL -> APPROVED`/`REJECTED` state machine as any other draft — `applyDraftTransition()` (Stage 6A, untouched) has no notion of "follow-up" at all. `SendApprovedDraftService.send()` is the only send path for a follow-up exactly as it is for an original message; every existing safety property (kill switch checked before preparing the write and again immediately before the network write, canonical-X-user-ID-only targeting, exact-approved-text-only, the existing `daily_limit_dms` rolling-24h check, dry-run short-circuit before any write, uniform audit-log entry on every outcome) applies unchanged, with the follow-up reply-recheck added as one additional gate ahead of the existing ones.

**Kill switch (Section J) / Limits (Section K).** No new kill-switch mechanism and no new rate-limit key — both a follow-up's eligibility recheck and its send still resolve through the single existing `KillSwitch`/`SystemConfigService.getDailyLimit('dms')`, shared with every other send. A kill-switch-active recheck reports `BLOCKED`, verified never to collide with a genuine `REPLIED`/`OPTED_OUT` result in the same test run.

**Dry run (Section L).** A follow-up dry-run performs the full check sequence — including the new reply-recheck — and still never contacts X or marks anything `SENT`, exactly like Stage 6B's dry-run; regression-tested directly for both an eligible dry-run (`DRY_RUN`) and a blocked one (`REPLIED`, with zero adapter calls in either case).

**Network failure (Section M).** Unchanged from Stage 6B: no automatic retry exists anywhere in this stage's diff, and an ambiguous network failure is still recorded as ambiguous and blocks any further automatic attempt — a follow-up send failure is handled by the exact same `mapSendError()`/`upsertOutreachMessage()` logic as an original send, now correctly keyed to the follow-up's own sequence step rather than the manual-send singleton.

**No autonomy (Section N).** Confirmed by grep sweep and by construction: no `cron`, `setInterval`, `setTimeout`-as-scheduler, queue library, "send all," or "run for every eligible prospect" method exists anywhere in `packages/outreach/src`. `FollowUpDraftService.generateFollowUpDraft()` and `SendApprovedDraftService.send()` each operate on exactly one caller-specified `(prospectId, sequenceId)` / `(draftId, prospectId)` pair per call — an operator (human or a future, explicitly-triggered script) must call each one explicitly, once per follow-up.

**No reply-detection duplication (Section O).** `FollowUpDraftService` and the extended `SendApprovedDraftService` both call the existing `FollowUpEligibilityService`/`ReplyDetectionService` (Stage 6C) — neither this stage's orchestrator nor its send extension re-implements X inbox fetching, conversation parsing, identity classification, or opt-out detection anywhere.

**Tests added:** 62 — `sequence-step.test.ts` (7), `follow-up-message-templates.test.ts` (8), `follow-up-draft-service.test.ts` (19, covering the full eligibility/sequence-mapping/personalization/approval-reuse matrix including the `NO_NEXT_STEP` distinction), `send-service-follow-up.test.ts` (14, covering sequence-aware dedup, the reply-recheck for every eligibility status including all 5 critical-invariant cases, backward compatibility with no `FollowUpEligibilityService` dependency, and dry-run). Plus 14 pre-existing Stage 6C tests re-verified unchanged immediately after the `sequence-step.ts` refactor, before any further Stage 6D code was written. Full suite: 680/680 passing (632 pre-existing + 48 net-new counted by vitest's own file totals — see exact per-file counts above), golden scores (63→C, 24→Reject, 100→A, 95→A, 83→B) unchanged (`scorer.test.ts` untouched and passing).

**Live X testing status.** Not performed and not claimed. Every test in this stage injects a scripted `XReplyDetectorAdapter`/`XSendAdapter`-shaped test double via the same constructor-injection pattern established in Stage 6B/6B-R/6C; no test calls the real vendored `client.request()` against x.com, and this environment's egress policy continues to block arbitrary outbound HTTP regardless.

**Known limitations.** (1) A follow-up's "exclude the original evidence" logic resolves the original draft via `outreach_messages.personalization_basis`'s stored `draftId` — if that original message was ever sent through a path that didn't populate `personalizationBasis` with a real `draftId` (not possible through any path this codebase currently exposes, but noted for completeness), the follow-up simply proceeds without an exclusion rather than erroring, which is a safe default (worst case: a follow-up could re-surface the same hook) but not a hard guarantee. (2) `FollowUpDraftService.pickIntent()` assumes sequence step 1 is always the original send and infers "first vs. subsequent vs. final follow-up" purely from `nextStepOrder`'s position — a sequence authored with an unconventional step-numbering scheme (e.g., not starting at 1, or with gaps) would still resolve a valid next step via `findNextSequenceStep()`, but the specific clarification/reminder/final_close labeling is a heuristic tied to the conventional 1-based, contiguous step-numbering already used throughout this codebase's own tests and Stage 6B's manual-send sequence. (3) Every limitation already documented in Stage 6C's own section (§2H) still applies unchanged, since this stage adds no new reply-detection or timing logic of its own.

**No scheduler, no autonomous follow-up sending, no bulk sending — by design and by construction, not by convention.** This stage stops exactly where its instructions require: a human (or an explicitly-invoked script) must call `FollowUpDraftService.generateFollowUpDraft()` for one prospect at a time, then separately approve the resulting draft, then separately call `SendApprovedDraftService.send()` for it. Building the actual operator-facing trigger for either of those calls (a CLI command, a dashboard button, a scheduled review queue) remains explicitly out of scope for a future stage.

## 2J. Stage 6E — Automation / Scheduling Foundation

**Architecture — five separated concerns, one narrow generic scheduler.** `Scheduled Run -> Find Due Work -> Validate Safety -> Create/Update Work Items -> Approval Boundary -> Optional Controlled Execution`, split cleanly across two packages: `AutomationScheduler` (`packages/core/src/automation/scheduler.ts`) knows nothing about X, prospects, or drafts — it only looks up a `JobHandler` by job type and runs it once, through the same `KillSwitch`/`JobRunner`/`audit_log` primitives every other stage already uses. All outreach-specific business logic (due-work discovery, reply refresh, draft preparation) lives in `packages/outreach/src/automation/` as three `JobHandler` implementations that orchestrate Stage 6C/6D services — never inside the scheduler itself. `AutomationScheduler` never imports, references, or could call `XSendAdapter`/`SendApprovedDraftService` — confirmed by grep sweep and by the class's own method list (`packages/outreach/test/automation/outreach-automation.test.ts`: "carries no method that could contact X to send a message").

**Job types (Section B) — DISCOVER/PREPARE, never SEND.** Exactly three: `discover_due_followups`, `refresh_reply_state`, `prepare_followup_drafts` (`packages/outreach/src/automation/job-types.ts`). No `SEND_DMS`/send-all job type exists anywhere — sending remains a human-triggered call to the existing `SendApprovedDraftService`, never something a scheduled job can reach.

**Approval-first default (Section C/K) — reuses Stage 1's existing `automation_mode`, no new enable/mode flags.** Rather than inventing `automation.enabled`/`automation.mode` config keys, this stage reuses `SystemConfigService.getAutomationMode('prospecting.outreach')` exactly as Stage 1 already defined it (`dry_run` | `approval_required` | `autonomous`, already fail-closing to `dry_run` when unset). `resolveOutreachAutomationDryRun()` maps `dry_run` -> every job runs in preview-only mode; `approval_required` and `autonomous` both permit real `PENDING_APPROVAL` draft creation, since **no job handler in this stage ever calls `submitForApproval` followed by `approve`, and none ever reaches `SendApprovedDraftService` at all** — setting `automation_mode` to `autonomous` is simply inert for this stage's own purposes, a statement of future intent for whenever a send-capable stage exists, not something this code interprets specially. The one new configuration key this stage does add — `outreach.automation_max_items_per_run` (default 25, `SystemConfigService.getOutreachAutomationMaxItemsPerRun()`) — was judged genuinely necessary (Section P's bound requirement) and is deliberately the *only* new key, per Section M's "prefer minimal configuration."

**Dry-run (Section D).** Only `prepare_followup_drafts` changes behavior under dry-run — it calls `DueWorkDiscoveryService.findDueFollowUps()` to report which candidates *would* get a draft (`wouldCreateDraftCount`) and creates nothing: no `outreach.draft.created` audit row, no `outreach_messages` row, no approval-state change. `discover_due_followups` and `refresh_reply_state` run identically regardless of the dry-run flag — both were already read-mostly/non-X-write operations by Stage 6C's own design (reply detection's `conversation_messages` persistence is not an X write and was already judged safe in Stage 6C; this stage adds no new write to either). `runOutreachAutomationJob`'s `forceDryRun` option can only ever ADD caution on top of a live-configured mode, never remove it — a configured `dry_run` mode always wins, regression-tested directly.

**Kill switch (Section E).** Checked first, before anything else — including the concurrency guard — in `AutomationScheduler.runScheduledJob()`. A kill-switch block returns `BLOCKED` (never conflated with "nothing due," `COMPLETED`, or `DRY_RUN`) and creates no `job_runs` row at all, since nothing was attempted. No second kill-switch implementation exists; the same `KillSwitch` class (Stage 1) is reused unchanged.

**Due-work discovery (Section H).** `DueWorkDiscoveryService` (`packages/outreach/src/automation/due-work-discovery-service.ts`) calls Stage 6C's `FollowUpEligibilityService.evaluate()` as the sole authority — no timing math is duplicated. The one Stage-6D-precedented addition, `NO_NEXT_STEP`, reuses the exact same shared `findNextSequenceStep()` helper `FollowUpDraftService` already uses, applied identically (distinguishing "no next-step defined" from every other `UNKNOWN` cause) — not a second implementation of that distinction. A local-only `ERROR` status (never part of Stage 6C's own `FollowUpEligibilityStatus` contract) marks a genuine exception during evaluation, keeping "our own code broke" structurally distinct from "the eligibility check legitimately came back UNKNOWN" (Section Q).

**Reply refresh (Section I).** `RefreshReplyStateHandler` calls Stage 6C's `ReplyDetectionService.detectReplies()` once per candidate prospect — no second X-inbox implementation, no re-derivation of reply state. A detection failure is reported by `ReplyDetectionService` itself as `UNKNOWN` (never `NO_REPLY` — Stage 6C's own invariant, unchanged) and never aborts the handler's loop; regression-tested directly ("a network error is never reported as NO_REPLY").

**Follow-up draft generation (Section J/K).** `PrepareFollowUpDraftsHandler` calls Stage 6D's `FollowUpDraftService.generateFollowUpDraft()` unchanged — no duplicated sequence logic, personalization, templates, or evidence gathering. The ONE piece of new orchestration this handler adds: for a freshly `DRAFTED` result, it calls the existing `OutreachDraftService.submitForApproval()` to advance the draft to `PENDING_APPROVAL` — guarded by `draft.status === 'DRAFTED'`, so a draft already at `PENDING_APPROVAL`/`APPROVED`/`REJECTED` is left untouched on a repeated run rather than re-submitted (which would otherwise throw `InvalidDraftTransitionError`). No handler anywhere calls `approve()` — regression-tested directly ("automation never calls approve() — an approved draft can only exist if a human approved it").

**Bounds (Section P).** Three independent bounds, all enforced: `ctx.maxItems` caps candidates considered (`findActiveSequenceCandidates`'s own `maxCandidates` parameter) and, for due-work discovery, is threaded through as `maxReplyChecks` too (`DueWorkDiscoveryService.findDueFollowUps` accepts the two as genuinely independent options and stops network-touching reply checks as soon as `maxReplyChecks` is hit even if more un-checked candidates remain) — regression-tested independently for both bounds.

**Idempotency (Section G) / duplicate protection.** `generateFollowUpDraft()`'s own existing idempotency (Stage 6D: at most one non-terminal draft per prospect) means a second `prepare_followup_drafts` run against unchanged state reuses the same draft rather than creating a second one; combined with the `submitForApproval` guard above, a third run still leaves exactly one draft at `PENDING_APPROVAL`. No new uniqueness mechanism was added — `outreach_messages`' existing `(prospect_id, sequence_id, sequence_step_order)` unique index remains the real backstop against ever sending the same follow-up step twice, entirely inherited from Stage 6D (this stage never calls `SendApprovedDraftService` at all, so it cannot itself create a duplicate send).

**Concurrency (Section T).** `AutomationScheduler` refuses to start a second concurrent run of the SAME job type: before starting a fresh (non-resume) run, it calls `JobRunner.findResumable(jobType)` — if a run of that type is still `pending`/`running`, the new attempt is refused with `BLOCKED` and the existing run's `job_run` id, rather than starting a competing one. This is per-job-type, not a global lock (three job types can run concurrently with each other) — judged sufficient because `job_runs`' own `findResumable` query already gives exactly this per-type visibility; no distributed lock or second concurrency primitive was added.

**Failure isolation (Section Q).** Every handler processes candidates in a loop with a per-item try/catch — one candidate throwing never aborts the run for the others (regression-tested directly in all three handlers' test files). The scheduler-level `runScheduledJob()` also wraps the entire handler invocation in try/catch, mapping an uncaught handler exception to `FAILED` (never silently swallowed, never miscategorized as `COMPLETED`). Three explicit failure-shape invariants hold throughout, all regression-tested: a network error during reply detection never becomes `NO_REPLY`; a `DueWorkDiscoveryService` evaluation exception never becomes `ELIGIBLE` (it becomes the module-local `ERROR` status instead); an ineligible/erroring candidate never becomes `DRAFTED`.

**Audit logging (Section R).** `AutomationScheduler` writes exactly one `automation.run.started`/`automation.run.completed`/`automation.run.failed`/`automation.run.blocked` row per run (job type, run id, item counts, dry-run flag, blocked/error reason) via the existing `writeAuditLog()` — which already refuses credential-shaped payload keys, regression-tested directly for this stage's own audit rows too. Each handler additionally writes a per-item audit row (`automation.due_followup.checked`, `automation.reply_refresh.failed`, `automation.followup_draft.submitted_for_approval` / `.would_create` / `.failed`) referencing `prospectId`/`sequenceId`/`draftId` where appropriate — never message content, never credentials.

**Run status vocabulary (Section S).** `COMPLETED` | `PARTIAL` | `BLOCKED` | `DRY_RUN` | `FAILED` (`AUTOMATION_RUN_STATUSES`, `packages/core/src/automation/scheduler.ts`). `PARTIAL` is used only when some items succeeded and some failed within one run; `FAILED` when every processed item failed OR the handler itself threw; `BLOCKED` covers both a kill-switch block and a concurrency refusal (distinguished by the result's own `reason` text, never conflated with a legitimate "nothing due" `COMPLETED`). `DRY_RUN` always takes priority in the reported status when the run was requested as dry-run, regardless of the handler's internal item counts.

**No autonomous send (Section U) — verified by construction and by test.** Zero `SEND_DMS` job type, zero call to `XSendAdapter`/`SendApprovedDraftService` anywhere in `packages/outreach/src/automation/` or `packages/core/src/automation/scheduler.ts` (confirmed by grep sweep). `PrepareFollowUpDraftsHandler` — the only handler capable of creating a draft — never calls `approve()`, only (conditionally) `submitForApproval()`. An operator must still explicitly approve a draft and explicitly call `SendApprovedDraftService.send()` for anything to ever reach X.

**Tests added:** 78 — `automation-scheduler.test.ts` (25, core: explicit run, dry-run, kill switch, bounded/deterministic/repeated run, run-status vocabulary, concurrency, checkpointing, audit logging, no-arbitrary-execution), `candidate-discovery.test.ts` (6), `due-work-discovery-service.test.ts` (14, including the full eligibility-status matrix, `NO_NEXT_STEP`/`ERROR` distinctions, and both independent bounds), `discover-due-followups-handler.test.ts` (4), `refresh-reply-state-handler.test.ts` (7), `prepare-followup-drafts-handler.test.ts` (11, covering approval boundary, full idempotency matrix, dry-run, and the REPLIED/NOT_DUE critical gates), `outreach-automation.test.ts` (11, end-to-end via the real factory, mode-resolution, bounds, kill switch, and the no-send-method security check). Full suite: 758/758 passing (680 pre-existing + 78 net new), golden scores (63→C, 24→Reject, 100→A, 95→A, 83→B) unchanged (`scorer.test.ts` untouched).

**Live X testing status.** Not performed and not claimed. Every test injects a scripted `XReplyDetectorAdapter` via the same constructor-injection pattern established in Stage 6B/6B-R/6C/6D; no test in this stage calls the real vendored `client.request()` against x.com, and this environment's egress policy continues to block arbitrary outbound HTTP regardless.

**Known limitations.** (1) `findActiveSequenceCandidates()` scans every `sent` `outreach_messages` row and deduplicates in application code (no SQL `DISTINCT`) — consistent with this codebase's existing precedent (`OutreachDraftService.listDraftsForProspect`), acceptable at this foundation scope and documented rather than worked around; a future stage should add an index-backed distinct query if candidate volume grows. (2) The concurrency guard is per-job-type and relies on `job_runs.status` staying accurate — a process that crashes mid-run leaves a `running` row that will correctly block a fresh run of that same job type from starting until an operator explicitly resumes (`resumeJobId`) or manually resolves the stuck row; there is no automatic staleness/heartbeat-timeout detection in this stage (mirroring `JobRunner`'s own existing scope — it was not asked to add one). (4) Every limitation already documented in Stage 6C (§2H) and Stage 6D (§2I) still applies unchanged, since this stage adds no new reply-detection, timing, personalization, or send logic of its own — it only orchestrates.

**No content engine (Section V).** Confirmed: no content generation, post scheduling, publishing, analytics, or engagement automation exists anywhere in this stage's diff — every new file lives under `packages/core/src/automation/` (the generic scheduler primitive) or `packages/outreach/src/automation/` (outreach-specific orchestration only).

## 2L. Stage 8 — X Publishing + Distribution Boundary

**Architecture — the exact chain, and only that chain.** `AutomationScheduler` (Stage 6E, reused, not duplicated) -> `PublishDueContentHandler` (`packages/content/src/automation/publish-due-content-handler.ts`) -> `PublishApprovedContentService` (`packages/content/src/publishing/publish-approved-content-service.ts`) -> `XPublishAdapter` (`packages/core/src/adapters/x-publish-adapter.ts`) -> `XManagerPublishAdapter` (`packages/adapters/src/xmanager-publish.adapter.ts`) -> verified `POST /2/tweets`. Confirmed by grep sweep (see Security audit below): `publishPost()` is called from exactly one call site in the entire repository — `PublishApprovedContentService.performRealPublish()`. No other file, including the new automation handler, ever imports or calls `XPublishAdapter` directly. This is the same "narrow adapter, one calling service, automation never touches the adapter" discipline Stage 6B/6B-R established for DM sending.

**Upstream publishing source and pinned commit.** Unlike DM sending (Stage 6B/6B-R), where the necessary write module had to be specially re-vendored from `xactions-http` after Stage 6B correctly stopped at an unverified format, the real, complete, VERIFIED implementation for public-post publishing already existed in this repository's own Stage 1 vendoring: `packages/content/vendor/x-manager` (source `https://github.com/tylerbuilds/x-manager`, pinned commit `a3534ba953fc88beac79fc12ca5ebbcd4f3bed2d`, MIT), specifically `src/lib/twitter-api-client.ts`'s `postTweet()` and its usage in `src/app/api/bridge/openclaw/post/route.ts`. Re-verified this stage via a fresh clone at the same pinned commit and a byte-diff of both files (plus `x-config.ts` and `package.json`) against the already-vendored copies — all four identical, confirming the existing snapshot is genuine and unmodified (the same discipline `xactions-http/VENDOR.md` documents for its own trimmed excerpt).

**Publishing transport, endpoint, payload, authentication (all verified from source, none guessed).** The official, documented **X API v2** `POST {xApiBaseUrl}/2/tweets` endpoint (`xApiBaseUrl` defaults to `https://api.x.com`) — a fundamentally different kind of dependency than `xactions-http`'s undocumented internal-GraphQL scraping, and the reason this stage did not need a Stage-6B-style "format unverified, stop here" blocker. Payload for this stage's text-only scope: `{"text": string}` — upstream's `media`/`community_id`/`reply` fields are deliberately excluded (out of scope; see "No unrelated features" below). Authentication is OAuth 1.0a user-context, `Authorization: OAuth ...`, generated per-request over the method+URL+`oauth_*` parameters only — the JSON body is never included in the signature base string, per the verified source's own explicit code comment for v2 endpoints ("do NOT include the request body in the OAuth signature"). Response: success -> `{"data": {"id": string, "text": string}}`; failure -> `{"errors": [{"message": string, "type"?: string}]}`, normalized by the vendored `normalizeErrorResponse` (byte-identical logic to upstream, TS->JS only) from whatever shape X's API actually returns. Full record, including the exact five documented deviations from upstream at the auth/config injection seam, in `packages/adapters/vendor/x-manager-http/VENDOR.md`.

**Zero new external dependencies for OAuth signing.** The verified source signs requests via the `oauth-1.0a` + `crypto-js` npm packages — confirmed NOT installed anywhere in this repository. Rather than add them, `packages/adapters/src/oauth1-signer.ts` is an ORIGINAL (not vendored) native reimplementation of the standard, publicly documented OAuth 1.0a / RFC 5849 HMAC-SHA1 algorithm using only Node's built-in `crypto` module — a decades-old, standardized spec, categorically different from the X-specific request format (which genuinely required source verification and is the part that IS vendored). It reproduces the verified source's own "never sign the request body for v2" rule exactly. Regression-tested for determinism given a fixed timestamp/nonce, for the signature changing under every one of method/URL/consumer-secret/token-secret, and for RFC 3986-correct percent-encoding.

**Character limit (Section P) — verified, not invented.** The verified source's own bridge layer defines `MAX_TWEET_CHARS = 280`, checked via `twitterWeightedLength()` (`src/lib/twitter-text.ts`), which implements X's own documented character-counting rule (https://developer.x.com/en/docs/counting-characters: every `http(s)://` URL weighs exactly 23 characters regardless of real length). This is X's own platform-wide standard limit for OAuth1 user-context text posts, not a number this stage invented. Reproduced as `packages/content/src/publishing/x-post-constraints.ts` (`MAX_X_POST_WEIGHTED_LENGTH = 280`, `xWeightedLength()`), applied ONLY as a `PublishApprovedContentService` pre-publish revalidation check — deliberately NOT folded into Stage 7's `validateContentDraft()` (a separate, additive, publish-time-only module, so Stage 7's own regression tests and draft-authoring-time behavior are completely untouched).

**`XPublishAdapter` (Section D) — one method, no escape hatch.** `publishPost({text}): Promise<{xPostId, publishedAt, publishedText}>` — no `request()`/`post()`/`execute()`/arbitrary-endpoint method exists or ever will, mirroring `XSendAdapter`'s exact narrow-contract discipline from Stage 6B. Deliberately separate from the much larger, still-unverified `XWriteAdapter` (Stage 1, unchanged — `postTweet`/`postThread`/`replyTo`/`sendDM`/`getInboxSince`/`getSessionHealth` all still throw `NotImplementedInStage1Error`), for the same reason `XSendAdapter` was kept separate rather than widening `XWriteAdapter`.

**`PublishApprovedContentService` (Section E) — the 10 responsibilities, in order, every call, no shortcuts.** (1) load the authoritative draft via `ContentDraftService.getDraft()` — never trusts a caller-supplied body; (2) verify `status === 'APPROVED'`; (3) verify approval integrity via `getApprovalIntegrity()` (see content-mutation below); (4) verify scheduling readiness + due-ness via `SchedulingReadinessService.getSchedulingState()`; (5) idempotency check against `content_drafts.x_manager_post_id`; (6) revalidate content fresh — re-runs Stage 7's `validateContentDraft()` PLUS the new X-length check, never trusting a stale `quality_check_status`; (7) kill switch, checked immediately before the boundary; (8) publishing mode (see below); (9) enforce the daily post limit (existing `daily_limit_posts` config key, previously defined in Stage 1, never wired to anything until now — reused, not duplicated); (10) call `XPublishAdapter.publishPost()`, persist `x_manager_post_id`, ingest an own-content-performance snapshot, and write an audit row. There is no other entry point — this service cannot be asked to "just publish this string."

**Approval boundary + content-mutation invalidation (Section F/W) — re-derived from the audit log every call, never a cached flag.** `ContentDraftService.getApprovalIntegrity(draftId)` folds the FULL audit trail: it records a SHA-256 `contentHash` of the draft body inside every `content.draft.approved` audit event (an additive field, added this stage — existing Stage 7 approval tests pass unmodified since they don't inspect the detail payload), and a new `updateBody()` method (also additive) writes a separate `content.draft.body_changed` event with the new body's hash WITHOUT touching `approval_status` in the DB or going through the `applyDraftTransition()` state machine (APPROVED remains terminal with no outgoing transitions, exactly as Stage 7 established — this stage adds no new transition to that table). `contentChangedSinceApproval` is `true` whenever the most recent body-changed event postdates the most recent approval event, or their hashes disagree. `PublishApprovedContentService` treats such a draft as NOT approved for publishing purposes, regardless of what the DB's `approval_status` column still says — regression-tested directly ("BLOCKED when the draft body changed after approval, without a fresh approve() call"; "publishes again once a mutated draft is re-approved, using the NEW text — approved text A never silently becomes published text B"). Re-approving an already-APPROVED draft (needed specifically for this re-approval flow, since the state machine treats APPROVE on APPROVED as a true no-op) is handled as a special case in `approve()` that writes a fresh audit event with the current hash without inventing a new state-machine transition.

**Scheduling vs. content mutation are independent axes (Section X) — regression-tested directly.** `SchedulingReadinessService` gained `scheduleFor()`/`getSchedulingState()` (additive), recording `content.draft.scheduled_for` as its own separate audit-event namespace. Rescheduling a draft (calling `scheduleFor()` again with a new timestamp) never touches approval state and is proven NOT to trigger `contentChangedSinceApproval` — directly regression-tested. Changing content, conversely, always requires the explicit re-approval flow above; a schedule change is never sufficient.

**Publishing modes (Section J) — reuses Stage 1's existing `content.publishing` `automation_mode`, adds exactly one new fail-closed confirmation gate.** `dry_run`: `PublishApprovedContentService` forces `dryRun = true` regardless of caller intent — the adapter is never called, no state is altered, and the result is `BLOCKED` with a reason string beginning `DRY_RUN:` naming exactly what would have been published (regression-tested: "never calls the adapter in dry_run mode"; "never alters draft state in dry_run mode" — the adapter mock's call count is asserted at zero in every dry-run test). `approval_required`: publishes for real, since the draft already carries a genuine human approval (Sections 2/3 above already enforce this — this mode requires nothing additional). `autonomous`: additionally requires a NEW, explicit `content.publishing.autonomous_enabled` `system_config` boolean (default/missing = `false`, fails closed) — set to `true` only by explicit human action; regression-tested both directions ("BLOCKED in autonomous mode when ... not explicitly set (fail closed)"; "publishes ... once ... explicitly true"). This is Section J's literal instruction ("AUTONOMOUS explicitly disabled unless all required conditions satisfied, fail closed if config missing") implemented as a second, independent gate rather than folded into the pre-existing 3-value mode enum.

**Dry-run guarantee, proven, not asserted.** Every dry-run test constructs the fake `XPublishAdapter` as a `vi.fn()` and asserts `toHaveBeenCalledTimes(0)` after the call — the claim "dry-run never calls the adapter" is verified by a spy, not inferred from reading the code.

**Limits (Section K).** Reuses the existing `daily_limit_posts` `system_config` key (defined in Stage 1, unused until this stage) via a rolling-24h count of `content_drafts` rows with a non-null `x_manager_post_id` and a recent `updated_at` — no second rate-limit framework. **Operating note:** this key has no default value; an operator who never explicitly sets it will see EVERY real publish attempt `BLOCKED` with "the configured daily post limit (0) has already been reached," per the existing `getDailyLimit()` fail-safe-to-zero contract (`system-config.ts`, unchanged) — a deliberate fail-closed default, not a bug, but worth calling out explicitly here so it is never mistaken for a broken publish path during setup.

**Idempotency (Section L) — investigated, and the answer is yes, a canonical ID exists and is used.** The verified `POST /2/tweets` response returns X's own canonical numeric post ID (`data.id`) directly — this is NOT a case requiring "document the exact uncertainty," unlike some upstream integrations. `content_drafts.x_manager_post_id` (an existing, previously-unpopulated column, documented since the original schema specifically for "an FK into the vendored X-Manager scheduler once scheduled/published") is the natural, zero-migration persistence point: `PublishApprovedContentService` checks it FIRST (step 5, before any network call) and short-circuits to a `PUBLISHED` result with the existing ID if already set — regression-tested directly, including "calling publishDraft twice for the same draft only calls the adapter once." What remains genuinely UNRESOLVED, and is documented rather than hidden: if the network request to X succeeds but the local process crashes/is killed BEFORE `x_manager_post_id` is persisted, a subsequent run would not see the column set and could re-publish (X's own API does not appear, from the verified source and its own tests, to offer a client-supplied idempotency-key parameter for this endpoint). This system therefore provides **at-least-once**, not exactly-once, semantics in that specific narrow crash window — documented here explicitly rather than a false exactly-once claim, per Section L's own instruction.

**Unknown outcomes and error mapping (Section M/N) — never converts ambiguity into a false claim in either direction.** `PublishResult.outcome` is exactly `PUBLISHED | BLOCKED | FAILED | UNKNOWN`. `XPublishNetworkError` (a network-level failure — connection/DNS/timeout, or a response whose body could not be read) and `XPublishUnexpectedError` (a malformed/unrecognized response shape) both map to `UNKNOWN` — in BOTH cases, whether X actually created the post cannot be determined from the failure alone, so it is never assumed FAILED (which could safely be retried, wrongly) or PUBLISHED (which would be worse). `XPublishAuthenticationRequiredError`/`XPublishRateLimitedError`/`XPublishInvalidContentError` all map to `FAILED` — genuine, definitive rejections where X never created the post, verified by the vendored transport's own HTTP status code (401/403 -> auth, 429 -> rate limit, 400/422 -> invalid content). None of this is inferred — `packages/adapters/vendor/x-manager-http/post-tweet.js` carries the HTTP status through in its return shape specifically so the adapter can classify without guessing. Regression-tested directly for every one of these mappings, plus "never marks the draft published on FAILED or UNKNOWN outcomes."

## 2M. Stage 9 — Performance Analytics + Learning Loop

**Architecture — closing the loop, honestly.** `PUBLISHED CONTENT -> COLLECT PERFORMANCE (identity-only, see gap below) -> ANALYZE (`PerformanceAnalysisService`) -> IDENTIFY PATTERNS (`pattern-detection.ts`) -> LEARN (`GrowthTechniqueLearningService`) -> IMPROVE RECOMMENDATIONS (`ContentRecommendationEngine` -> `WeeklyContentPlanService`)`. Every new subsystem lives under `packages/content/src/analytics/`, is read/recommend-only, and reuses Stage 6E's `AutomationScheduler` (zero new scheduler) via four additive job types. No subsystem in this stage can approve, publish, mutate a draft's body, or contact a prospect — confirmed by grep sweep (Security audit, below).

**Metrics available vs. unavailable (Section A/C) — investigated, not assumed.** `XReadAdapter.TweetResult` (Stage 4A, unchanged through Stages 7/8) carries `{id, authorUsername, text, createdAt, url}` — NO impressions/likes/replies/reposts/bookmarks/quotes/profile-visit/follower-change fields exist anywhere in this contract, re-confirmed this stage. The only genuinely available signal for a specific published post is engager IDENTITY, via `XReadAdapter.getEngagers(tweetUrl)` (Stage 4A, previously unused in this codebase) — likers/repliers/quoters as `{username, userId?, displayName?}`, never a count of any of those actions and never the reply TEXT itself. `searchTweets()` (also Stage 4A) DOES return tweet text, and is the only path this stage found to real reply/mention content — used for business-intent collection (Section G), not per-post metrics. Every metric this stage cannot obtain stays `null` in `OwnPostMetricsSnapshot` — never defaulted to zero, unchanged from Stage 7's own rule, re-verified via a dedicated dashboard test ("never fabricates a metric: a post with no impressions never contributes a fake reach score").

**Post identity (Section B).** No second post-identity was created. `content_drafts.x_manager_post_id` (Stage 8's own column) remains the single canonical X post ID; the full chain `ContentIdea -> ContentDraft -> Approval (audit_log) -> Scheduled (audit_log) -> x_manager_post_id -> OwnPostMetricsSnapshot (audit_log, entity_id = the same post ID)` is unchanged and re-verified traceable end-to-end.

**Performance snapshots (Section C) — no new table.** `OwnContentPerformanceService` (Stage 7) already IS the snapshot model this section asks for: `ingestSnapshot()` never overwrites a prior observation (each call is a new, timestamped `audit_log` row keyed by `content.performance.ingested`/entity_id=postId), preserves X post ID/captured timestamp/available metrics, and `getLatestSnapshot()` reads the most recent one without ever averaging across history. This stage's only schema-adjacent change is additive: a `ctaType` field on `OwnPostMetricsSnapshot` (derived from `text` exactly like `hookType`/`painCategory` already were) and a `businessIntent` field added to `ContentSignalExtraction`'s existing flexible JSON — neither required touching a table definition. The one genuine schema touch was widening `content_signals.signal_type`'s TypeScript `$type<>()` union to add `'own_post_engagement'` (a new logical signal type for replies/mentions ON Metrivio's own posts, distinct from `'own_post'`, the post itself) — this is a `$type<>()` annotation on an existing `text` column with no `CHECK` constraint at the SQL level, so it required NO Drizzle migration (verified: `drizzle/migrations/` unchanged, `git status` confirms no new migration file). No new table was created anywhere in this stage.

**Metric normalization (Section D).** `PerformanceAnalysisService.scoreSnapshot()` computes an engagement RATE only when impressions (the denominator) is present — never divides by a missing/zero denominator, regression-tested directly. Reach and engagement are each normalized to a fixed 0-100 scale via a documented saturation point (10,000 impressions = full reach credit) rather than ever compared as raw counts against another account, mirroring `ExpertPerformanceAnalysisService`'s (Stage 7) own per-audience-size-fair discipline.

**ICP engagement (Section F) — built on the existing `prospects` identity, not a fresh guess.** `IcpEngagementClassifier` matches an engager against an EXISTING `prospects` row (by X user ID first, username as a case-insensitive fallback) — deliberately NOT a fresh bio-based role inference at engagement time, even though the reused Stage 4B `classifyFounderCandidate()` bio classifier would have been available; a `prospects` row already passed Stage 4B's own discovery/classification process, which this stage judged is what "confidently established" (Section F's own phrase) requires. No match -> `UNKNOWN`, always, regression-tested directly including "never infers ICP status from a username alone... even if it looks founder-like." `prospects.source`'s `'content_engagement'` enum value — defined since Stage 4B's original schema and never used until now — is the value this classification is intended to feed if a future stage wires up creating new `prospects` rows from engagement (deliberately NOT built this stage, to keep the change read-only; see Known Limitations).

**Business intent (Section G) — deterministic keyword rules over ACTUAL reply text, collected via `searchTweets()`.** `classifyBusinessIntent()` returns `GENUINE_INTENT` only for a fixed, documented set of phrase patterns naming Metrivio/methodology/diagnostics/measurement/marketing-efficiency/a request to talk or DM/a "for my store" qualifier — a bare positive reaction ("love this", "🔥") is always `GENERIC_ENGAGEMENT`, regression-tested directly ("never classifies a generic positive reaction as business intent"). `UNKNOWN` is reserved for the case of NO text at all (a bare like), never used as a dumping ground for "text exists but isn't intent." `CollectPostPerformanceHandler` stores a qualifying mention (`GENUINE_INTENT` OR a resolved ICP match) as a NEW `content_signals` row (`signalType: 'own_post_engagement'`) — a non-qualifying mention is never stored, keeping the signal table meaningful (mirrors `IcpResearchService`'s own "only signal when it clears a bar" rule).

**Content-value model (Section H).** `scoreContentValue()` weights Business Intent (40) and ICP (30) more than Engagement (20) and Reach (10) — documented, fixed, and regression-tested directly to prove raw reach alone cannot reach `HIGH_VALUE`. A missing sub-score is excluded from BOTH the numerator and denominator of the weighted average, never treated as zero — regression-tested directly. All four sub-scores missing -> `UNKNOWN`, never a fabricated default.

**Winner/loser detection (Section I/J) — folded into `PerformanceAnalysisService`'s own group output, not a separate module** (a deliberate simplification: `patternStrength` — Section I's "require repeated evidence" — and `performanceDirection` — Section J's PROMISING/NEUTRAL/UNDERPERFORMING — are two independent axes computed for every topic/pillar/hook/format/CTA group, which together ARE what Sections I/J ask for). (3) `prospects.source`'s `'content_engagement'` value is read by this stage's `IcpEngagementClassifier` but this stage never WRITES a new `prospects` row from an engagement discovery — a confidently-identified engager who is not already a `prospects` row is simply `UNKNOWN`, not auto-enrolled; wiring automatic prospect creation from qualifying engagement is a reasonable future extension, deliberately not built here to keep this stage read-only over prospect data. (4) `BenchmarkingService`'s topic-gap detection compares pain-taxonomy category strings against `content_ideas.pillar`/`topic` values — a genuine vocabulary mismatch (rather than a true content gap) could theoretically produce a false-positive gap if a future stage renames pillars inconsistently; documented here as a known coupling, not a bug found. (5) `PerformanceAnalysisService`'s content-value scoring saturation points (10,000 impressions, engagement-rate scaling) are documented, reasonable defaults, not derived from any real observed Metrivio traffic (since no real reach data exists yet per limitation 2) — they should be revisited once genuine reach data is available.

## 3. Single-Maintainer / Small-Project Dependency Risk

**Risk:** XActions (428 stars, 1 primary maintainer), X-Manager (16 stars, 1 primary maintainer), and now **OpenTechAnalyzer** (Houseofmvps/opentechalyzer, 1–2 stars, very new — RESEARCH.md §2A) are all small projects. If any goes unmaintained, we inherit their maintenance burden or must migrate. This is somewhat elevated for XActions specifically since its write path is architecturally load-bearing (it's the DM-sending implementation, not just a read-side fallback), and OpenTechAnalyzer is the smallest, newest project of the three despite now being the confirmed, verified, primary technology-detection dependency.

**Likelihood:** Medium over a multi-month horizon.
**Impact:** Medium — contained by the adapter pattern (§6 of ARCHITECTURE.md); a maintenance stall means forking/patching a pinned version ourselves, not a rewrite. Since DM sending depends on XActions specifically and all technology evidence depends on OpenTechAnalyzer specifically, both are worth a closer watch than a purely secondary/fallback dependency would warrant.

**Mitigations:**
- Pin exact versions/commits, never track `main`, for all three.
- Vendor (fork) X-Manager specifically, since it's the write-path backbone — control exactly when upstream changes land.
- **This is the concrete, legitimate reason wappalyzergo remains documented as a fallback `TechAnalyzerAdapter` implementation**, per the founder's own instruction that wappalyzergo may stay "if your research shows a legitimate reason to keep it": OpenTechAnalyzer's small size and short commit history is exactly that reason. It is not a reflection of any doubt about OpenTechAnalyzer's license, capability, or the decision to make it primary — it's ordinary dependency risk hygiene applied evenly, the same reasoning already applied to XActions and X-Manager.
- Since the entire built-in OpenTechAnalyzer fingerprint database is itself MIT-licensed and stated in its own README to be "written for this project" (not copied from elsewhere), forking it ourselves if upstream maintenance stalls is straightforward and unencumbered — lower fork risk than a project built on top of someone else's restrictively-licensed data would carry.

## 3A. Licensing Boundary — Optional GPL-3.0 External Fingerprint Database

**Risk:** OpenTechAnalyzer's core, built-in 588-fingerprint database is MIT. It also supports an optional `opentechalyzer db import` command that pulls in a wider, community-maintained fingerprint dataset (`enthec/webappanalyzer`), which is **GPL-3.0**. The project's own documentation states this data is fetched to the user's own machine on request and never redistributed by the project itself, so running `db import` does not relicense OpenTechAnalyzer or Metrivio's codebase — but it does mean a machine that has run `db import` is holding GPL-3.0 data locally.

**Likelihood:** Low as a legal issue (this is a well-understood, deliberately-designed license boundary, not an accidental trap), but worth a clear operating rule so it's never crossed absentmindedly.
**Impact:** Low if the rule below is followed; potentially meaningful if violated (redistributing GPL-3.0 data as part of a distributed product can trigger copyleft obligations on that distribution).

**Operating rule:** Metrivio's default deployment does **not** run `opentechalyzer db import`. The built-in MIT-licensed 588-fingerprint database already covers every technology named in the founder's brief (Shopify, Klaviyo, Gorgias, Recharge, Yotpo, Meta Pixel, GA4, GTM — all independently confirmed, RESEARCH.md §2A.7). If broader, long-tail fingerprint coverage is ever wanted beyond DTC/ecommerce-and-marketing-stack technologies, `db import` can be run on a self-hosted instance for internal use only — but no Metrivio deployment artifact (Docker image, distributable package, hosted service) should ever bundle or redistribute the resulting GPL-3.0 dataset.

## 3C. Licensing Boundary — LGPL-3.0-or-later Transitive Dependency in Vendored X-Manager (Stage 2 Finding)

**Risk:** The vendored X-Manager instance (`packages/content/vendor/x-manager`) depends on `next@15.5.12`, whose `package.json` lists `sharp@^0.34.3` as an **optional** dependency (used only for `next/image`'s built-in server-side image optimization). `sharp` itself is Apache-2.0, but at each supported platform it pulls in a prebuilt native binary package, `@img/sharp-libvips-<platform>@1.2.4`, whose declared license is **LGPL-3.0-or-later** — confirmed directly by inspecting `packages/content/vendor/x-manager/package-lock.json` (`node_modules/@img/sharp-libvips-*` entries, each `"license": "LGPL-3.0-or-later"`, each `"optional": true`). X-Manager's own `next.config.mjs` does not disable image optimization, and `next/image` is used in at least one component (`src/components/CreateThreadFromArticle.tsx`), so this is not a theoretical/unused transitive dependency — it is plausibly exercised at runtime once the vendored app is actually deployed in production (`output: 'standalone'` mode, where Next.js recommends installing `sharp` since no bundled fallback exists).

**Likelihood:** Low as a legal issue — this is npm's ordinary optional-native-binary distribution pattern (the same shape as `better-sqlite3`'s prebuilt binaries), and LGPL's dynamic-linking allowance is exactly the case here: `sharp` calls into libvips via prebuilt shared-library bindings, not by statically linking libvips source into a combined binary, and Metrivio does not modify libvips itself.
**Impact:** Low if the operating rule below is followed; a genuine concern only if libvips were ever statically linked into a single distributed binary, or if its source were modified without republishing those modifications.

**Operating rule:** No action is required to keep using `sharp`/`next/image` as vendored today — standard `npm install` preserves the `@img/sharp-libvips-*` packages' own license files, and dynamic linking to an unmodified LGPL-3.0 library does not extend copyleft to the calling application. Before any change that would statically bundle these native binaries into a single compiled artifact (e.g. a packaging tool that inlines native addons), re-verify this reasoning first. This entry exists because the LGPL dependency itself is real and worth a named, documented rule — not because Stage 1 had already flagged it (it had not; RISK_REGISTER.md's only licensing entries before this Stage 2 pass were §3 and §3A, both about OpenTechAnalyzer, not X-Manager).

## 4. Data Fabrication Risk (Prospecting)

**Risk:** An LLM-assisted enrichment or personalization step could hallucinate a revenue figure, ad spend number, technology, or founder fact not actually present in the source evidence — directly violating the brief's core constraint.

**Likelihood:** Medium if evidence-gating is not enforced at the code layer (LLMs will do this if merely instructed not to and given the option).
**Impact:** High — this is a named, explicit constraint from the founder; violating it undermines the entire premise of the ICP scoring system and could produce embarrassing/false outreach claims.

**Mitigations:**
- Evidence-gating is enforced structurally, not just via prompt instruction: personalization and scoring logic only ever read from the `evidence` table with a valid tier; there is no code path that lets a draft or a score reference a fact absent from that table.
- Every LLM call used for extraction (e.g., "does this bio suggest a founder role?") writes its output back as an `evidence` row with an explicit tier (never higher than `LIKELY` for a single unverified LLM read), rather than being treated as ground truth.
- Golden/adversarial test cases (Stage 3, Stage 10 of BUILD_PLAN.md) specifically probe for fabrication before those stages are considered done.

## 5. Data Fabrication Risk (Content — Case Studies / Proof)

**Risk:** The content engine could generate copy implying Metrivio has existing clients, results, or case studies, contradicting Proof Document Part B's explicit "no case studies yet, and that's fine" positioning.

**Likelihood:** Medium without an explicit check (this is a very natural LLM failure mode — writing confident-sounding marketing copy).
**Impact:** High — directly contradicts the founder's explicit instruction and could be reputationally costly if published.

- Founder-experience claims (Unilever/P&G) are only permitted when attributed to the founder personally, never phrased as Metrivio client work — checked by the same quality gate.
- All generated content passes through human approval by default regardless of the quality check's pass/fail result — the quality check is a pre-filter, not a substitute for review.

## 6. Evidence Tier Misapplication Risk

**Risk:** The scoring engine's evidence tiers (CONFIRMED/STRONG EVIDENCE/LIKELY/UNKNOWN) are precisely defined in the ICP document with a fixed corroboration rule. A subtle implementation bug (e.g., allowing 2+ STRONG EVIDENCE signals to round up to CONFIRMED) would silently produce inflated scores and, worse, incorrectly unlock dollar-figure disclosure language that should be gated behind CONFIRMED status.

**Likelihood:** Low once golden tests are in place; Medium during initial implementation before those tests exist.
**Impact:** High — an incorrectly "CONFIRMED" prospect could trigger outreach copy stating a specific revenue or spend figure that was never actually confirmed, which is both a factual and a credibility problem.

**Mitigations:** Stage 3 of BUILD_PLAN.md requires the golden worked-examples from ICP §22.F to pass exactly before any other code is allowed to depend on the scorer, plus explicit property tests asserting STRONG EVIDENCE can never become CONFIRMED via corroboration.

## 8. Restart / Duplicate-Action Risk

**Risk:** A process restart mid-sequence could, without care, re-send an outreach message or re-publish a scheduled post.

**Likelihood:** Low with the designed mitigations; Medium if skipped under time pressure.
**Impact:** Medium-High — a duplicate cold DM to a prospect who already replied "not interested" is exactly the kind of thing that damages both the prospect relationship and, at scale, account standing.

**Mitigations:** DB-level unique constraints on `(prospect_id, sequence_id, sequence_step_order)` (DATABASE.md §2) and a pre-send stop-condition re-check immediately before every send (ARCHITECTURE.md §3.1) — not just at sequence start. Chaos-tested explicitly in BUILD_PLAN.md Stage 15.

## 9. Credential Exposure Risk

**Risk:** X session cookies, OAuth tokens, or API keys leaking into logs, source control, or the audit trail.

**Likelihood:** Low with discipline; this is a "one careless log line" class of risk, so it needs an explicit control, not just good intentions.
**Impact:** High — a leaked session cookie or OAuth token is equivalent to full account takeover risk.

**Mitigations:** `audit_log.detail` is schema-documented as never containing credential material (DATABASE.md §4); encryption-at-rest for stored credentials (X-Manager's existing AES-256-GCM pattern, reused rather than reinvented); `.env`-based secrets never committed; Stage 15 hardening pass includes an explicit grep-for-secrets check across code and logs before considering the build production-ready.
